\section{L'Hyperconvergence (HCI)}

\par Cette section définit le concept d'hyperconvergence, présente ses composantes et ses avantages, puis le compare à l'architecture traditionnelle.\\

\subsection{Définition}

\par L'hyperconvergence (HCI, ``Hyper-Converged Infrastructure'') est une architecture qui regroupe dans un même système le calcul, le stockage et le réseau, pilotés par une couche logicielle centralisée. On n'a plus besoin de gérer des équipements distincts pour chaque fonction~\cite{ref2}.\\

\par L'infrastructure hyperconvergée repose sur trois composantes fondamentales :\\

\begin{itemize}

    \item \textbf{Le calcul} : des processeurs virtuels (vCPU, ``Virtual Central Processing Unit'') alloués dynamiquement aux machines virtuelles.

    \item \textbf{Le stockage} : un système de stockage distribué logiciel, agrégé à partir des disques locaux de chaque n\oe{}ud.

    \item \textbf{Le réseau} : un switch virtuel logiciel permettant la segmentation et l'isolation du trafic réseau.

\end{itemize}

\subsection{Avantages de l'hyperconvergence}

\par Par rapport aux architectures traditionnelles où le calcul, le stockage et le réseau sont gérés séparément, l'HCI offre plusieurs avantages :\\

\begin{itemize}

    \item \textbf{Simplicité d'administration} : une interface unique pour gérer l'ensemble des ressources.

    \item \textbf{Réduction des coûts matériels} : pas besoin de baies de stockage ou de switchs réseau dédiés.

    \item \textbf{Évolutivité horizontale} : l'ajout d'un n\oe{}ud augmente simultanément la capacité de calcul, de stockage et de réseau.

    \item \textbf{Haute disponibilité native} : la réplication des données entre les n\oe{}uds assure la continuité de service en cas de panne.

\end{itemize}

\section{Comparaison : Solutions Propriétaires et Open Source}

\par Cette section met en regard les solutions propriétaires et les solutions open source dans le contexte du projet.\\

\subsection{Solutions propriétaires}

\par Les solutions propriétaires comme VMware vSAN ou Nutanix offrent un bon support et des fonctionnalités avancées, mais elles posent plusieurs problèmes dans notre contexte :\\

\begin{itemize}

    \item \textbf{Coûts élevés} : les licences et la maintenance annuelle représentent un investissement important, difficilement justifiable pour des environnements de test.

    \item \textbf{Dépendance fournisseur (``Vendor Lock-in'')} : la migration vers une autre solution est souvent complexe et coûteuse.

    \item \textbf{Faible flexibilité} : les environnements propriétaires offrent peu de liberté pour personnaliser l'infrastructure.

\end{itemize}

\subsection{Solutions open source}

\par Les solutions open source présentent plusieurs avantages dans notre contexte :\\

\begin{itemize}

    \item \textbf{Indépendance technologique} : aucune dépendance vis-à-vis d'un éditeur.

    \item \textbf{Absence de coûts de licence} : seuls les coûts matériels et de main-d'\oe{}uvre sont à prévoir.

    \item \textbf{Transparence et auditabilité} : le code source est accessible et modifiable.

    \item \textbf{Communauté active} : documentation abondante et mises à jour régulières.

\end{itemize}

\par Pour des environnements de test et de petits déploiements, l'approche open source est clairement la plus adaptée.\\

\section{Analyse des Solutions Open Source HCI}

\par Le critère principal de sélection est la légèreté et la capacité à fonctionner de façon stable sur un cluster de 3 n\oe{}uds.\\

\subsection{OpenStack}

\par OpenStack est une plateforme cloud open source complète, utilisée par de nombreuses grandes entreprises. Elle propose des services de calcul (Nova), stockage objet (Swift), stockage en bloc (Cinder), réseau (Neutron), identité (Keystone), etc.\\

\par Cependant, OpenStack présente des inconvénients majeurs pour notre cas d'usage :\\

\begin{itemize}

    \item \textbf{Complexité de déploiement} : l'installation implique l'orchestration de nombreux services interdépendants, ce qui rend le déploiement long et difficile à maintenir.

    \item \textbf{Consommation de ressources élevée} : les services de base consomment plusieurs Go de RAM avant même de démarrer des VMs.

    \item \textbf{Inadapté aux petits clusters} : OpenStack est conçu pour des déploiements de grande envergure. Sur 3 n\oe{}uds, ses performances et sa stabilité sont compromises.

\end{itemize}

\subsection{Harvester HCI}

\par Harvester est une solution HCI open source développée par SUSE, basée sur Kubernetes et KubeVirt. Elle propose une interface moderne et une intégration native avec Rancher~\cite{ref5}.\\

\par Ses limites dans notre contexte :\\

\begin{itemize}

    \item \textbf{Consommation en RAM et CPU élevée} : la couche Kubernetes sous-jacente consomme beaucoup de ressources avant même d'allouer quoi que ce soit aux VMs.

    \item \textbf{Maturité relative pour les VMs classiques} : Harvester est davantage orienté vers les conteneurs. La gestion de VMs Linux/Windows classiques y est moins optimisée~\cite{ref4}.

\end{itemize}

\subsection{Proxmox VE}

\par Proxmox Virtual Environment (VE) est une plateforme de virtualisation open source basée sur KVM et LXC. Elle propose une interface web centralisée, un support natif de Ceph et une gestion intégrée du clustering et de la haute disponibilité~\cite{ref6}.\\

\par Ses atouts pour notre cas d'usage :\\

\begin{itemize}

    \item \textbf{Légèreté} : moins de 1 Go de RAM consommé à vide, laissant l'essentiel des ressources aux VMs.

    \item \textbf{Déploiement rapide} : un cluster de 3 n\oe{}uds est opérationnel en quelques heures.

    \item \textbf{Interface web intuitive} : la console (accessible sur le port 8006) centralise la gestion des VMs, conteneurs, stockage, réseau et haute disponibilité.

    \item \textbf{Intégration native de Ceph} : les outils Ceph sont intégrés directement dans Proxmox, ce qui simplifie beaucoup le déploiement.

    \item \textbf{Communauté active} : documentation officielle complète et forums très actifs.

\end{itemize}

\section{Présentation des Technologies Retenues}

\par Cette section présente en détail les trois technologies open source retenues : Proxmox VE, Ceph et Open vSwitch.\\

\subsection{Proxmox VE : L'hyperviseur}

\paratitle{Présentation générale}

\par Proxmox Virtual Environment (VE) est une plateforme de virtualisation open source basée sur un noyau Linux Debian modifié. Elle supporte deux types de virtualisation : \textbf{KVM} (``Kernel-based Virtual Machine'') pour les machines virtuelles complètes compatibles avec Linux, Windows et BSD, et \textbf{LXC} (``Linux Containers'') pour les conteneurs légers. L'ensemble est administré via une interface web sur le port 8006.\\

\paratitle{La pile de virtualisation : KVM, QEMU et libvirt}

\par La virtualisation dans Proxmox repose sur une pile logicielle à trois niveaux qui collaborent ensemble.\\

\paratitle{KVM: Kernel-based Virtual Machine}

\par KVM est un module du noyau Linux (chargé via \texttt{kvm.ko} et \texttt{kvm\_intel.ko} ou \texttt{kvm\_amd.ko} selon le processeur) qui transforme Linux en hyperviseur de type 1~\cite{refKVM}. KVM exploite les extensions matérielles \textbf{Intel VT-x} ou \textbf{AMD-V} pour exécuter le code des VMs directement sur le CPU physique sans émulation. Les instructions non privilégiées s'exécutent à vitesse native, tandis que les instructions privilégiées (accès mémoire, I/O) sont interceptées par le noyau hôte. Le résultat est une performance CPU très proche du bare metal, entre 95\% et 99\% des performances natives.\\

\paratitle{QEMU: Quick EMUlator}

\par QEMU est l'émulateur de machine qui accompagne KVM~\cite{refQEMU}. Il opère en espace utilisateur et assure plusieurs fonctions :\\

\begin{itemize}

    \item Il \textbf{émule les périphériques} de la VM : carte réseau virtuelle (VirtIO, e1000, RTL8139), contrôleur de disque (VirtIO SCSI, IDE, SATA), carte graphique, USB (``Universal Serial Bus''), BIOS (``Basic Input/Output System'') ou UEFI (``Unified Extensible Firmware Interface'') via OVMF (``Open Virtual Machine Firmware''). Chaque VM correspond à un processus \texttt{qemu-system-x86\_64} sur l'hôte.

    \item Il gère le \textbf{CPU virtuel (vCPU)} : le nombre de c\oe{}urs, le modèle de CPU exposé à la VM (host-passthrough, kvm64, Haswell, Broadwell, etc.) et les flags CPU visibles par le système invité.

    \item Il assure la \textbf{gestion mémoire} : allocation de RAM, support du ``Memory Ballooning'' et des ``Huge Pages'' pour réduire la pression sur le TLB.

    \item Il fournit les \textbf{interfaces de migration} pour la live migration : QEMU transfère l'état complet d'une VM (mémoire, état CPU, état des périphériques) vers un autre hôte sans interruption de service.

\end{itemize}

\par Quand KVM est disponible, QEMU lui délègue l'exécution du code de la VM et ne s'occupe que des périphériques. C'est cette combinaison KVM+QEMU qui constitue l'hyperviseur réel.\\

\paratitle{libvirt : couche d'abstraction de la virtualisation Linux}

\par libvirt est une bibliothèque open source qui offre une API unifiée pour gérer plusieurs hyperviseurs (KVM, QEMU, LXC, Xen)~\cite{refLibvirt}. Elle est utilisée par des outils comme \texttt{virt-manager}, OpenStack Nova ou oVirt.\\

\par Proxmox ne l'utilise pas : il a sa propre couche de gestion en Perl (\texttt{PVE::QemuServer}) qui pilote QEMU directement. Ça lui donne un contrôle plus précis sur les paramètres QEMU et une meilleure intégration avec l'API REST (``Representational State Transfer'') et les mécanismes de cluster.\\

\paratitle{Les conteneurs Linux : LXC}

\par LXC (``Linux Containers'') est une virtualisation légère basée sur deux mécanismes du noyau Linux : les \textbf{namespaces} et les \textbf{cgroups}. Contrairement aux VMs KVM qui ont un noyau dédié, les conteneurs LXC partagent le noyau de l'hôte, ce qui réduit beaucoup la consommation de ressources : un conteneur démarre en quelques secondes avec un surcoût mémoire de quelques dizaines de mégaoctets.\\

\par Les \textbf{namespaces} isolent chaque conteneur (processus, réseau, points de montage, utilisateurs). Les \textbf{cgroups} (``control groups'') limitent et comptabilisent la consommation de ressources (CPU, mémoire, I/O) par conteneur.\\

\par Proxmox intègre LXC nativement avec des modèles pour Debian, Ubuntu et Alpine. LXC est adapté pour les services qui ne nécessitent pas de noyau spécifique : agents de supervision, serveurs NTP, services PXE, intégration continue~\cite{ref39}.\\

\paratitle{Gestion du cluster : Corosync et le quorum}

\par La gestion du cluster Proxmox repose sur \textbf{Corosync}, un framework de communication qui assure le consensus entre les n\oe{}uds via un mécanisme de quorum~\cite{ref20}. Corosync envoie des messages ``heartbeat'' réguliers sur un réseau dédié pour détecter les défaillances. Un cluster Proxmox nécessite au minimum \textbf{3 n\oe{}uds} pour garantir un quorum stable.\\

\par Avec 3 n\oe{}uds, la majorité est de 2 : si un n\oe{}ud tombe, les 2 restants gardent le quorum et le cluster continue. Si 2 n\oe{}uds tombent en même temps, le n\oe{}ud restant se met en retrait pour éviter le ``split-brain'', une situation où deux parties du cluster modifient les données en même temps sans le savoir.\\

\paratitle{Haute disponibilité (HA Manager)}

\par Proxmox intègre un gestionnaire de haute disponibilité composé de deux services~\cite{refHA} :\\

\begin{itemize}

    \item \textbf{pve-ha-crm} (``Cluster Resource Manager'') : le cerveau centralisé du HA. Il surveille toutes les ressources protégées (VMs, conteneurs) et prend les décisions de basculement.

    \item \textbf{pve-ha-lrm} (``Local Resource Manager'') : l'agent local sur chaque n\oe{}ud. Il exécute les ordres du CRM et remonte l'état des ressources locales.

\end{itemize}

\par Quand un n\oe{}ud devient inaccessible, le CRM déclenche le \textbf{fencing} (isolation forcée via le watchdog), puis redémarre les VMs protégées sur les n\oe{}uds survivants. Le délai typique est de 60 à 120 secondes. Les VMs avec leurs disques sur Ceph RBD peuvent redémarrer sur n'importe quel n\oe{}ud sans déplacer de données.\\

\paratitle{Live Migration}

\par La migration à chaud (``live migration'') déplace une VM en cours d'exécution d'un n\oe{}ud vers un autre sans interruption perceptible. Proxmox l'implémente via QEMU en trois phases :\\

\begin{enumerate}

    \item \textbf{Pré-copie mémoire} : QEMU copie les pages mémoire de la VM vers le n\oe{}ud cible pendant que la VM tourne. Les pages modifiées (``dirty pages'') sont recopiées lors de passes successives.

    \item \textbf{Basculement} : quand le volume de dirty pages devient assez faible, la VM est brièvement suspendue, les dernières pages sont transférées, puis la VM reprend sur le n\oe{}ud cible.

    \item \textbf{Nettoyage} : les ressources de la VM sont libérées sur le n\oe{}ud source.

\end{enumerate}

\par C'est ce mécanisme que le service CLBS utilise pour redistribuer la charge entre les n\oe{}uds. Le trafic de migration doit transiter sur un réseau dédié pour ne pas impacter les autres flux.\\

\paratitle{Interface de gestion et API REST}

\par Proxmox expose une \textbf{API REST complète} sur le port 8006 (HTTPS), utilisée aussi bien par l'interface web que par des outils externes. Toutes les opérations disponibles graphiquement le sont aussi via l'API : création de VMs, gestion du stockage, déclenchement de migrations, consultation des métriques. Les appels sont authentifiés par ticket de session.\\

\subsection{Ceph : Le stockage distribué}

\par Ceph est une solution de stockage distribué open source (``Software-Defined Storage'') qui fonctionne sur du matériel standard (serveurs x86) et qui se répare automatiquement en cas de panne~\cite{ref27}. C'est le choix retenu pour la couche de stockage de notre infrastructure.\\

\paratitle{Architecture de Ceph}

\par Ceph repose sur un composant central appelé RADOS (``Reliable Autonomic Distributed Object Store''), qui gère la réplication et la répartition des données sur le cluster. Autour de RADOS, plusieurs types de démons travaillent ensemble :\\

\begin{itemize}

    \item \textbf{Ceph Monitor (MON) :} Les Moniteurs maintiennent une carte du cluster (``cluster map'') et assurent le consensus entre les n\oe{}uds via un quorum. C'est eux qui décident de l'état du cluster en cas de désaccord.

    \item \textbf{Ceph Manager (MGR) :} Le Manager collecte les métriques du cluster en temps réel (utilisation, performances) et les expose via une interface web et des APIs externes.

    \item \textbf{Ceph OSD (Object Storage Daemon) :} L'OSD gère un disque physique et s'occupe de la lecture, de l'écriture, de la réplication et du rééquilibrage des données. Dans notre architecture hyperconvergée, chaque n\oe{}ud héberge des OSDs en plus de l'hyperviseur.

    \item \textbf{Ceph Metadata Server (MDS) :} Ce démon est spécifique au système de fichiers CephFS. Pour un usage en mode bloc (disques de VMs), il n'est pas nécessaire.

\end{itemize}

\paratitle{La gestion intelligente des données : CRUSH et Placement Groups}

\par Ceph utilise un algorithme appelé CRUSH (``Controlled Replication Under Scalable Hashing'')~\cite{ref28} pour déterminer où stocker chaque objet. Contrairement aux systèmes classiques, un client peut calculer directement l'emplacement d'un objet sans interroger un serveur central, ce qui évite un point de défaillance unique.\\

\par La carte CRUSH définit l'organisation physique du cluster avec des ``domaines de défaillance'' (n\oe{}uds, racks, salles). Ceph place les répliques sur des n\oe{}uds distincts pour qu'une panne matérielle n'entraîne pas de perte de données.\\

\par Pour gérer les milliers d'objets efficacement, Ceph les regroupe en unités logiques appelées Placement Groups (PGs), une couche intermédiaire entre les objets et les OSDs qui améliore l'équilibrage des données dans le cluster.\\

\paratitle{Les modes de protection des données}

\par Ceph propose deux mécanismes pour protéger les données :\\

\begin{itemize}

    \item \textbf{Réplication :} Chaque objet est dupliqué en N copies (généralement 3), chacune sur un OSD différent. En cas de panne, les données restent disponibles sur les autres répliques. C'est le mode utilisé dans ce projet : avec 3 n\oe{}uds et un facteur de réplication 3, le cluster tolère la perte d'un n\oe{}ud complet.

    \item \textbf{Erasure Coding (Codage d'effacement) :} Les données sont découpées en K fragments de données et M fragments de parité (K+M au total), répartis sur différents OSDs. On peut tolérer la perte de M fragments. Ce mode est plus économe en espace (1,5× contre 3× pour la réplication) mais plus coûteux en calcul lors de la reconstruction. Il est surtout utilisé pour les données froides ou l'archivage.

\end{itemize}

\paratitle{Intégration de Ceph dans une architecture hyperconvergée}

\par L'intégration entre Ceph et Proxmox VE est native : on peut créer et gérer un cluster Ceph directement depuis l'interface web de Proxmox.\\

\par Dans notre architecture, chaque n\oe{}ud joue deux rôles en même temps : il exécute des VMs via KVM et contribue au stockage distribué via ses disques Ceph. Les volumes des VMs sont fournis via Ceph RBD (``RADOS Block Device''), distribués et répliqués sur tout le cluster.\\

\par Les avantages de Ceph dans ce contexte sont :\\

\begin{enumerate}

    \item \textbf{Évolutivité horizontale} : l'ajout d'un n\oe{}ud apporte du calcul et du stockage en même temps, avec rééquilibrage automatique des données.

    \item \textbf{Haute disponibilité} : pas de point de défaillance unique, les données restent accessibles même si un serveur tombe.

    \item \textbf{Auto-réparation} : en cas de panne d'un disque ou d'un n\oe{}ud, le cluster recrée automatiquement les répliques manquantes sur les autres n\oe{}uds.

    \item \textbf{Coût maîtrisé} : Ceph est gratuit et fonctionne sur du matériel standard, bien moins coûteux que des SAN (``Storage Area Network'') ou des appliances propriétaires.

    \item \textbf{Gestion simplifiée} : l'outil \texttt{cephadm} permet un déploiement conteneurisé, et l'intégration avec Proxmox réduit la complexité administrative.

\end{enumerate}

\subsection{Open vSwitch (OVS) : La virtualisation réseau}

\paratitle{Présentation générale}

\par Open vSwitch (OVS) est un commutateur logiciel open source distribué sous licence Apache 2.0, conçu pour les environnements de virtualisation~\cite{ref8}. Il repose sur deux composants : \texttt{ovs-vswitchd}, le démon qui implémente le switch avec son module noyau, et \texttt{ovsdb-server}, une base de données de configuration persistante. Il supporte nativement les VLANs 802.1Q, le bonding LACP (``Link Aggregation Control Protocol''), NetFlow, sFlow, QoS, et les tunnels GRE (``Generic Routing Encapsulation''), VXLAN et Geneve~\cite{ref9}.\\

\par Dans notre cluster HCI, OVS joue le rôle de commutateur central sur chaque n\oe{}ud et gère la segmentation de tout le trafic depuis un bridge virtuel unique.\\

\paratitle{Pourquoi segmenter le réseau dans un cluster HCI ?}

\par Dans un cluster HCI, plusieurs types de trafic cohabitent sur la même infrastructure physique avec des profils très différents :\\

\begin{itemize}

    \item La \textbf{réplication Ceph} génère un trafic continu à très haute bande passante qui peut saturer un réseau partagé.

    \item Les \textbf{heartbeats Corosync} sont très sensibles à la latence : un délai peut déclencher un basculement non voulu du cluster.

    \item Les \textbf{migrations à chaud} produisent des pics de transfert intenses lors du déplacement de la mémoire d'une VM entre deux n\oe{}uds.

    \item Les \textbf{charges de travail applicatives} génèrent un trafic imprévisible qui ne doit pas interférer avec les flux d'infrastructure.

\end{itemize}

\par Sans isolation, ces flux se dégradent mutuellement. C'est le même problème que Nutanix résout avec la séparation entre le trafic du contrôleur interne et celui des VMs. La solution est d'affecter à chaque type de trafic un segment réseau dédié géré par OVS.\\

\par La documentation Proxmox et les guides Ceph recommandent explicitement de séparer le réseau de réplication interne Ceph, le réseau d'accès des VMs au stockage et le réseau de synchronisation du cluster.\\

\paratitle{Les neuf types de trafic à isoler}

\par On identifie neuf types de trafic aux profils distincts, chacun justifiant un segment dédié. Le plan d'adressage exact est défini dans le chapitre suivant ; ici on explique juste pourquoi chaque isolation est nécessaire :\\

\begin{itemize}

    \item \textbf{Administration et gestion :} accès à l'interface web, SSH, API. Volume faible mais disponibilité permanente requise. Ce segment doit être isolé des réseaux applicatifs pour empêcher tout accès non autorisé depuis une VM compromise.

    \item \textbf{Synchronisation du cluster :} heartbeats et consensus Corosync. Très sensible à la latence : tout délai peut déclencher un basculement non souhaité.

    \item \textbf{Réplication interne du stockage distribué :} communications entre OSDs pour la réplication et la reconstruction des données. Flux continu à haute bande passante, ne doit pas être mélangé avec d'autres trafics.

    \item \textbf{Accès des machines virtuelles au stockage :} flux entre les VMs et le pool Ceph. Séparé du réseau de réplication interne pour que les opérations de rééquilibrage ne pénalisent pas les VMs.

    \item \textbf{Migrations à chaud :} transferts de mémoire entre n\oe{}uds lors des migrations. Flux ponctuel mais intense, isolé pour ne pas saturer les autres réseaux.

    \item \textbf{Machines virtuelles de production :} trafic applicatif exposé aux utilisateurs. Accessible uniquement via le répartiteur de charge, isolé des environnements de développement.

    \item \textbf{Machines virtuelles de test et de développement :} isolé de la production pour éviter toute interférence.

    \item \textbf{Zone exposée :} services accessibles depuis l'extérieur, protégés par le pare-feu et le répartiteur de charge.

    \item \textbf{Sauvegarde :} transferts de sauvegardes et d'instantanés. Flux soutenu, maintenu hors bande pour ne pas dégrader les performances en production.

\end{itemize}

\paratitle{Contrainte d'infrastructure rencontrée et adaptation : adoption de VXLAN}

\par L'architecture initiale prévoyait une segmentation par \textbf{VLANs 802.1Q}, ce qui nécessite que le switch physique soit configuré en mode ``trunk''. Cette approche est standard et supportée par OVS.\\

\par Cependant, sur l'infrastructure de Sonatrach, les trois serveurs Dell R720 sont connectés à un switch administré par l'équipe réseau de l'entreprise. Ce switch a déjà des VLANs définis (VLAN 10 pour le management, VLAN 20 pour un usage interne), et l'équipe projet n'a aucun droit d'administration dessus. Les serveurs sont connectés en mode access sur le VLAN de gestion uniquement.\\

\par Face à cette contrainte, on a remplacé les VLANs 802.1Q par des tunnels \textbf{VXLAN} (``Virtual eXtensible LAN'', RFC 7348)~\cite{refVXLAN}.\\

\paratitle{VXLAN : principe de fonctionnement}

\par VXLAN encapsule des trames Ethernet (niveau 2) dans des paquets UDP/IP (niveau 4), créant des réseaux virtuels superposés (``overlay networks'') sur un réseau physique existant sans le modifier.\\

\par Quand une VM sur le n\oe{}ud A veut communiquer avec une VM sur le n\oe{}ud B, OVS encapsule la trame dans un paquet UDP vers l'IP de B. Le switch physique voit juste du trafic UDP ordinaire. À la réception, OVS sur B désencapsule le paquet et restitue la trame à la VM destination.\\

\par Chaque réseau logique est identifié par un \textbf{VNI} (``VXLAN Network Identifier''), un entier sur 24 bits, l'équivalent fonctionnel d'un tag VLAN. Chacun des neuf types de trafic correspond à un tunnel VXLAN avec son propre VNI. L'attribution précise des VNIs est détaillée dans le chapitre suivant.\\

\paratitle{Impact sur l'architecture et bilan}

\par Le passage à VXLAN ne change pas l'architecture à neuf segments. Les neuf segments (management, Corosync, Ceph interne, Ceph public, migration, VMs prod, test/dev, DMZ, backup) sont conservés, chacun avec un VNI dédié à la place d'un tag VLAN. OVS gère tout ça de façon transparente, sans toucher au réseau physique de Sonatrach.\\

\par Cette approche apporte même quelques avantages : le cluster est indépendant du réseau physique sous-jacent et peut fonctionner sur n'importe quel réseau IP. VXLAN est d'ailleurs le protocole standard des grandes infrastructures cloud (AWS, Azure, GCP)~\cite{refVXLAN}, ce qui renforce la crédibilité technologique du projet. Et avec 16 millions de VNIs possibles contre 4 094 VLANs 802.1Q, la scalabilité future est largement couverte.\\

\par Le seul inconvénient est un surcoût d'encapsulation de 50 octets par paquet UDP, mais c'est négligeable sur des liaisons Gigabit ou 10 Gigabit Ethernet.\\

\section{L'Équilibrage Dynamique de Charge dans les Clusters Virtualisés}

\par Cette section expose la problématique du déséquilibre de charge, passe en revue les mécanismes existants, puis présente l'algorithme CSLB sur lequel s'appuie le CLBS développé dans ce projet.\\

\subsection{Problématique du Déséquilibre de Charge}

\par Dans un cluster de virtualisation, les VMs sont placées sur des n\oe{}uds lors de leur création et y restent sans mécanisme actif de redistribution. Avec le temps, la charge se répartit inégalement : certains n\oe{}uds peuvent être saturés à plus de 90\,\% de CPU tandis que d'autres restent à moins de 20\,\%. Ça dégrade les performances des VMs sur les n\oe{}uds chargés et gaspille les ressources des n\oe{}uds sous-chargés.

\subsection{Mécanismes d'Équilibrage dans les Plateformes Existantes}

\par VMware vSphere propose le \textbf{DRS} (``Distributed Resource Scheduler'')~\cite{ref18}, qui analyse en continu les métriques de charge et déclenche des migrations à chaud (vMotion) pour redistribuer les VMs. Le DRS ne migre que si le gain attendu dépasse un seuil configurable, pour éviter des déplacements inutiles.

\par D'autres plateformes proposent des mécanismes similaires : \textbf{Microsoft SCVMM} avec la ``Dynamic Optimization''~\cite{refSCVMM} pour Hyper-V, \textbf{oVirt} avec son planificateur de cluster via libvirt~\cite{refOvirt}, et \textbf{OpenStack Nova} avec son planificateur distribué par filtres et pondérations~\cite{refNova}.

\par Proxmox VE n'a pas de tel mécanisme natif. Ce projet développe un service équivalent, nommé CLBS, s'appuyant sur l'API REST Proxmox et le stockage partagé Ceph.

\subsection{L'Algorithme CSLB : Base Théorique du CLBS}

\par Le CLBS est fondé sur l'algorithme CSLB de Wilcox pour les environnements de virtualisation distribués~\cite{ref38}. L'algorithme repose sur un scheduler centralisé qui opère en cinq phases~\cite{ref17} :\\

\begin{enumerate}
    \item \textbf{Évaluation de la charge :} lecture des métriques CPU et RAM de chaque n\oe{}ud sur une fenêtre temporelle glissante, pour s'affranchir des pics instantanés.
    \item \textbf{Détermination de rentabilité :} calcul d'une bande modérée autour de la moyenne du cluster. Les n\oe{}uds hors de cette bande sont candidats à une action.
    \item \textbf{Calcul du vecteur de transfert :} quantité de ressources à migrer pour ramener le n\oe{}ud surchargé dans la bande.
    \item \textbf{Sélection de la VM :} la VM dont la charge correspond le mieux au vecteur de transfert.
    \item \textbf{Exécution de la migration :} live migration vers le n\oe{}ud avec la charge la plus faible.
\end{enumerate}

\par La live migration n'est possible que si le stockage est partagé entre tous les n\oe{}uds. Avec Ceph RBD, le disque d'une VM est accessible depuis n'importe quel n\oe{}ud sans déplacer de données~\cite{ref14}.

\section{Outils Complémentaires d'Infrastructure}
% ============================================================

\par En plus des trois technologies principales (Proxmox VE, Ceph, Open vSwitch), l'infrastructure utilise plusieurs outils complémentaires : répartition de charge applicative, supervision, automatisation, provisionnement réseau, pare-feu, synchronisation temporelle et intégration continue.\\

\subsection{HAProxy : Équilibrage de Charge Applicatif}

\par HAProxy (``High Availability Proxy'') est un proxy TCP/HTTP open source pour la haute disponibilité et l'équilibrage de charge~\cite{ref26}. Il agit comme point d'entrée unique pour un ensemble de serveurs, distribue les requêtes selon différents algorithmes (round-robin, moins de connexions, hachage par IP source) et vérifie la disponibilité des backends via des contrôles de santé. Si un backend tombe, HAProxy redirige automatiquement le trafic sans interruption pour l'utilisateur.

\subsection{Stack de Supervision : InfluxDB, Prometheus et Grafana}

\par Pour superviser l'infrastructure, on a besoin d'outils qui collectent, stockent et visualisent les métriques en temps réel : charge des n\oe{}uds, état du stockage, historique des migrations et alertes. Trois outils complémentaires forment cette stack.\\

\par \textbf{InfluxDB}~\cite{ref24} est une base de données orientée séries temporelles (``time series database''), optimisée pour les données horodatées à haute fréquence. Elle reçoit les métriques Proxmox (CPU, RAM, réseau, stockage) via le mécanisme natif ``Metric Server'' sans agent supplémentaire. Ces données sont utilisées par Grafana pour la visualisation et par le CLBS pour ses décisions de migration.\\

\par \textbf{Prometheus}~\cite{refPrometheus} collecte les métriques par interrogation HTTP selon un modèle de données par étiquettes. Il surveille le cluster Ceph via son point d'accès natif et les métriques du service CLBS.\\

\par \textbf{Grafana}~\cite{ref25} est l'outil de visualisation connecté aux deux sources précédentes. Il affiche des tableaux de bord unifiés sur l'état des n\oe{}uds, du stockage et du CLBS, avec des règles d'alerte configurables.\\

\subsection{Ansible : Automatisation d'Infrastructure}

\par Ansible~\cite{refAnsible} est un outil d'automatisation (``Infrastructure as Code'') qui exécute des playbooks YAML via SSH, sans agent sur les machines cibles. Un playbook décrit l'état cible d'une machine et Ansible l'applique de façon \textbf{idempotente} : si c'est déjà configuré, rien ne se passe.

\par Les playbooks sont organisés en tâches séquentielles sur un inventaire YAML. Les seuls prérequis sont SSH et les droits \texttt{sudo}. On l'utilise pour intégrer de nouveaux n\oe{}uds au cluster, provisionner des VMs et des conteneurs, et promouvoir des environnements de développement vers la production.

\subsection{PXE et TFTP : Provisionnement Réseau}

\par PXE (``Preboot eXecution Environment'') permet à un serveur de démarrer depuis le réseau sans support local. Il repose sur trois protocoles :\\

\begin{itemize}
    \item \textbf{DHCP :} attribution d'une adresse IP temporaire et indication du serveur de boot (options DHCP 66 et 67).
    \item \textbf{TFTP} (``Trivial File Transfer Protocol'', UDP/69) : téléchargement du bootloader. C'est le seul protocole utilisable dans un firmware pre-OS.
    \item \textbf{HTTP :} téléchargement de l'image d'installation (plusieurs centaines de Mo). TFTP ne convient pas aux gros fichiers car il n'a pas de contrôle de flux.
\end{itemize}

\par Ce mécanisme a été utilisé pour l'installation automatique de Proxmox VE sur les serveurs physiques.

\subsection{OPNsense : Pare-feu et Sécurité Périmétrique}

\par OPNsense~\cite{refOPNsense} est une distribution de pare-feu open source basée sur FreeBSD. Il assure le filtrage stateful des flux, la gestion des règles par interface et par VLAN, et des fonctionnalités avancées comme la détection d'intrusion (Suricata), le VPN (``Virtual Private Network'') et le portail captif. Dans notre infrastructure, OPNsense est le point de contrôle entre les segments internes et l'extérieur, notamment pour protéger la zone exposée (DMZ).

\subsection{NTP : Synchronisation Temporelle}

\par La synchronisation temporelle est critique dans un système distribué. Une dérive d'horloge entre les n\oe{}uds peut créer des incohérences dans les journaux, perturber Corosync et Ceph, et fausser les métriques de supervision. Le protocole NTP (``Network Time Protocol'')~\cite{refNTP} synchronise l'horloge de chaque n\oe{}ud sur un serveur de référence. Un serveur NTP interne au cluster garantit une base de temps commune pour tous les composants.

\subsection{GitLab CE : Intégration et Déploiement Continus}

\par GitLab CE (``Community Edition'')~\cite{ref40} est une plateforme DevOps open source avec un gestionnaire Git, un système CI/CD (``Continuous Integration / Continuous Deployment'') et des pipelines d'automatisation. Dans notre contexte, GitLab versionne les configurations d'infrastructure (playbooks Ansible, fichiers de configuration), déclenche les déploiements automatisés et maintient une traçabilité complète des modifications.

Les fondements de l'algorithme CLBS ont été établis, et les outils complémentaires ont été présentés. Le chapitre suivant détaille la conception de l'architecture proposée.\\
