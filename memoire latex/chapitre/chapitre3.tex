\section{\color{bleu}Introduction}

\par Ce chapitre présente la conception détaillée de l'infrastructure Cloud privée hyperconvergée proposée. Sur la base des technologies retenues dans le chapitre précédent — Proxmox VE, Ceph et Open vSwitch — nous décrivons ici les choix architecturaux guidant la construction de chaque couche de l'infrastructure. Nous présentons également la conception du mécanisme d'équilibrage dynamique de charge CLBS, ainsi que les outils d'automatisation retenus pour le déploiement et le provisionnement.\\

\par L'objectif de ce chapitre est de fournir une vision complète et cohérente de l'architecture avant toute phase d'implémentation, en justifiant chaque décision par des contraintes techniques, des recommandations officielles ou des exigences fonctionnelles identifiées précédemment.\\

\section{\color{bleu}Vue Globale de l'Architecture}

\par L'architecture proposée repose sur un modèle à trois couches superposées et interdépendantes, chacune apportant une dimension essentielle à l'infrastructure hyperconvergée.\\

\par La première couche est la \textbf{couche physique}, constituée de trois serveurs Dell PowerEdge R720 mis à disposition par le Centre d'innovation de Sonatrach. Proxmox VE est installé directement en mode bare metal sur chacun de ces serveurs, sans couche de virtualisation intermédiaire, ce qui garantit des performances maximales.\\

\par La deuxième couche est la \textbf{couche de virtualisation et de cluster}, composée des trois nœuds Proxmox (PVE-01, PVE-02, PVE-03) interconnectés via le réseau Sonatrach. Ces nœuds forment un cluster haute disponibilité géré par Corosync. Chaque nœud exécute simultanément les daemons Ceph pour le stockage distribué et une instance Open vSwitch avec des tunnels VxLAN pour la segmentation réseau. Cette convergence des rôles est l'expression directe du principe HCI.\\

\par La troisième couche est la \textbf{couche applicative et de services}, hébergeant la VM OPNsense pour le routage et le pare-feu, les VMs de démonstration Sona-Web, le mécanisme CLBS, la stack de monitoring, et les outils d'automatisation Ansible.\\

\subsubsection{Mécanisme de Quorum et Corosync}

\par Corosync est le framework de communication utilisé par Proxmox pour assurer le consensus entre les nœuds. Il envoie des messages de heartbeat à intervalles réguliers via le VxLAN 20. Le quorum dans un cluster de trois nœuds est atteint dès que deux nœuds sur trois sont opérationnels. La perte simultanée de deux nœuds entraîne le gel du cluster pour prévenir toute corruption des données.\\

\subsubsection{Haute Disponibilité}

\par Le mécanisme de haute disponibilité de Proxmox s'appuie sur Corosync pour la détection des pannes et sur le Resource Manager HA pour les décisions de basculement. Lorsqu'un nœud est déclaré défaillant, le HA Manager identifie les VMs concernées et déclenche leur redémarrage automatique sur un nœud survivant. Ce mécanisme est rendu possible par le stockage partagé Ceph : les disques des VMs étant accessibles depuis n'importe quel nœud, le redémarrage ne nécessite aucun transfert de données préalable. Le délai de basculement est typiquement compris entre 60 et 120 secondes.\\

\par Toutes les VMs de l'application Sona-Web sont configurées en mode HA, avec une priorité de basculement définie : HAProxy en premier, suivi des serveurs Flask, puis de la base PostgreSQL.\\

\subsection{\color{bleuu} Mécanisme d'Équilibrage Dynamique : CLBS}

\subsubsection{Contexte et Besoin}

\par Proxmox VE intègre un mécanisme de haute disponibilité réactif : lorsqu'un nœud tombe en panne, les VMs sont redémarrées sur les nœuds survivants. Cependant, Proxmox ne dispose d'aucun mécanisme proactif d'équilibrage de charge, contrairement à VMware vSphere qui propose le DRS (Distributed Resource Scheduler). Sans équilibrage proactif, un nœud peut être saturé à 90\% de CPU tandis qu'un autre reste à 20\%, dégradant les performances et gaspillant les ressources disponibles.\\

\subsubsection{Base Algorithmique : CSLB}

\par Notre mécanisme, nommé \textbf{CLBS (Central Load Balancing Scheduler)}, est une adaptation du CSLB (Central Scheduler Load Balancing). L'algorithme original repose sur cinq phases : évaluation de charge, détermination de rentabilité, calcul du vecteur de transfert, sélection de VM, et exécution de la migration. La charge CPU de chaque nœud est évaluée par rapport à un seuil dynamique (moyenne des charges de tous les nœuds) :

\[
\text{seuil} = \frac{\sum_{i=1}^{n} \alpha_i}{n}, \quad \text{diff} = \left|\text{seuil} - \frac{\alpha_{min} + \alpha_{max}}{2}\right|
\]

\par La bande modérée est définie à $\pm\max(\text{diff},\ 10\%)$ autour du seuil. Les nœuds hors de cette bande sont candidats à une action d'équilibrage.\\

\subsubsection{Modifications Apportées au CSLB}

\par Notre adaptation introduit plusieurs modifications importantes par rapport à l'algorithme original.\\

\begin{itemize}
    \item \textbf{Implémentation en Go :} retenu pour sa faible empreinte mémoire, sa gestion native de la concurrence via les goroutines, et la simplicité du déploiement sous forme de binaire statique dans un service systemd.

    \item \textbf{Extension à la RAM :} le CSLB original ne considère que le CPU. Notre implémentation calcule une bande modérée indépendante pour la RAM. Un nœud est surchargé si l'une ou l'autre dépasse sa bande respective.

    \item \textbf{Seuil minimum de migration :} une migration n'est déclenchée que si la charge dépasse un seuil absolu de 50\% (CPU ou RAM), évitant des déplacements inutiles dans un cluster globalement sous-chargé.

    \item \textbf{Sélection du nœud destination pondérée :} le choix du nœud de destination se fonde sur un score pondéré :
    \[
    \text{score} = \Delta_{CPU} \times 0.7 + \Delta_{RAM} \times 0.3
    \]
    Avant validation, CLBS simule l'état post-migration du nœud cible pour s'assurer que l'ajout de la VM ne le fait pas dépasser la bande haute.

    \item \textbf{Exclusion des VMs système :} OPNsense, la VM monitoring et la VM CLBS sont explicitement exclues du périmètre de migration.

    \item \textbf{Cadence et unicité :} CLBS s'exécute toutes les 60 secondes et ne peut déclencher qu'une seule migration par cycle.

    \item \textbf{Cooldown post-migration :} une période de repos de 5 minutes est appliquée après chaque migration, le temps que les métriques InfluxDB intègrent l'impact du changement.

    \item \textbf{Mécanismes anti-oscillation :} si une même VM est migrée deux fois en moins de 10 minutes, elle est gelée 30 minutes et l'administrateur est notifié. Si 6 migrations ou plus sont enregistrées en 30 minutes, le service se suspend automatiquement pendant une heure (circuit breaker).

    \item \textbf{Collecte des métriques :} CLBS combine l'API REST Proxmox pour les métriques courantes, et InfluxDB via le client Go officiel pour les moyennes glissantes sur 5 minutes, garantissant des décisions fondées sur des données lissées plutôt que sur des pics instantanés.
\end{itemize}

\subsubsection{Algorithme de Décision (Pseudocode)}

\begin{lstlisting}[style=sonacode,language={},caption={Pseudocode de l'algorithme CLBS},label={lst:clbs-pseudo}]
toutes les 60 secondes :
  recuperer metriques CPU et RAM moyennees (5 min) depuis InfluxDB
  calculer seuil_cpu, bande_moderee_cpu
  calculer seuil_ram, bande_moderee_ram

  pour chaque noeud N :
    si (cpu_N > bande_haute_cpu OU ram_N > bande_haute_ram)
       ET (cpu_N > 50% OU ram_N > 50%) :

      candidats_vm = VMs sur N non migrees recemment (cooldown 10 min)
      vm_cible = VM dont la charge est la plus proche du
                 vecteur de transfert calcule (phase 3 CSLB)

      pour chaque noeud destination D (bande legere) :
        score_D = (cpu_N - cpu_D) * 0.7 + (ram_N - ram_D) * 0.3
      noeud_dest = D avec score_D maximal

      si noeud_dest trouve :
        declencher live migration vm_cible -> noeud_dest
          via API Proxmox (VxLAN 50)
        enregistrer migration dans InfluxDB
        appliquer cooldown anti-oscillation (10 min sur vm_cible)
\end{lstlisting}

\subsection{\color{bleuu} Application de Démonstration : Sona-Web}

\subsubsection{Architecture Applicative}

\par Sona-Web est une application web déployée sur le cluster pour démontrer les capacités de haute disponibilité et de live migration. Elle est constituée de quatre VMs Debian 12 interconnectées :\\

\begin{itemize}
    \item \textbf{HAProxy (VM-201, 192.168.10.111:8080) :} point d'entrée unique de l'application. Il distribue les requêtes HTTP entre les deux serveurs applicatifs selon l'algorithme round-robin et surveille leur disponibilité toutes les 200 ms (\texttt{GET /health}), basculant vers l'instance disponible en moins de 200 ms (\texttt{fall 1}) en cas d'indisponibilité.

    \item \textbf{Flask app-1 (VM-202, 192.168.10.112:8000) et app-2 (VM-203, 192.168.10.114:8000) :} deux instances identiques de l'application Python Flask. Chaque instance enregistre de manière asynchrone en base de données toutes les requêtes reçues.

    \item \textbf{PostgreSQL (VM-204, 192.168.10.115:5432) :} base de données centralisée dont le disque est stocké sur un volume Ceph RBD, garantissant un historique cohérent quel que soit le nœud hébergeant les VMs applicatives.
\end{itemize}

\par Les quatre VMs sont membres du groupe HA \texttt{sona-group} et leurs disques résident sur le pool Ceph RBD partagé. Les adresses IP sont configurées de manière statique pour garantir leur stabilité après migration.\\

\subsubsection{Scénario de Validation HA}

\par Le scénario de validation se déroule en plusieurs temps : affichage de l'alternance round-robin entre app-1 et app-2, puis déclenchement d'une live migration de VM-202 (\texttt{app-1}) vers un autre nœud. Pendant la migration, Proxmox transfère l'état mémoire de la VM sans l'arrêter. Lorsque la synchronisation atteint \textasciitilde{}99\%, la VM est suspendue quelques dizaines de millisecondes le temps de transférer le delta final, puis reprend sur le nœud cible.\\

\par HAProxy détecte l'indisponibilité transitoire en 200 ms maximum et redirige l'intégralité du trafic vers app-2. Une fois la migration terminée, app-1 est remise en service dès le premier health check réussi (\texttt{rise 1}). La requête suivante permet de vérifier la répartition post-migration :\\

\begin{lstlisting}[style=sonacode,language=SQL,caption={Vérification de la répartition des requêtes en base},label={lst:sona-sql}]
SELECT instance_id,
       COUNT(*) AS total
FROM requests
WHERE request_time > NOW() - INTERVAL '1 hour'
GROUP BY instance_id;
\end{lstlisting}

\subsection{\color{bleuu} Architecture du Monitoring}

\par La stack de monitoring est déployée dans un conteneur LXC dédié à l'adresse \texttt{192.168.10.99}. Elle comprend trois composants complémentaires couvrant des périmètres de métriques distincts.\\

\par \textbf{InfluxDB} reçoit les métriques générales de Proxmox (CPU, RAM, réseau, stockage des nœuds et des VMs) via le mécanisme natif \textit{Metric Server}, sans agent supplémentaire. Cet historique est utilisé à la fois par Grafana pour la visualisation et par le service CLBS pour ses décisions de migration.\\

\par \textbf{Prometheus} collecte les métriques détaillées du cluster Ceph via l'endpoint exposé par le nœud MGR actif sur le port \texttt{9283}. Les métriques applicatives du service CLBS sont également exposées sur le port \texttt{9101} de la VM dédiée.\\

\par \textbf{Grafana} est connecté à InfluxDB et à Prometheus comme sources de données, permettant de construire des tableaux de bord unifiés couvrant l'ensemble de l'infrastructure : utilisation des ressources par nœud, état du cluster Ceph, historique des migrations CLBS, et alertes de surcharge.\\

\subsection{\color{bleuu} Automatisation}

\subsubsection{Ansible : Périmètre et Playbooks}

\par Ansible est l'outil d'automatisation principal, exécuté depuis les postes de travail des développeurs via SSH sur le réseau de management. Trois playbooks couvrent les principaux besoins d'automatisation.\\

\begin{itemize}
    \item \textbf{Playbook 1 — Intégration d'un nouveau nœud :} automatise l'ensemble de la procédure d'intégration d'un serveur fraîchement installé (via PXE) dans le cluster existant. Il couvre la configuration réseau OVS/VxLAN, l'adhésion au cluster Corosync, l'initialisation de l'OSD Ceph, et la configuration des exports de métriques vers InfluxDB.

    \item \textbf{Playbook 2 — Provisionnement de VMs :} automatise la création de VMs et de conteneurs LXC à partir de templates cloud-init stockés dans le pool Ceph. Il intègre la configuration réseau via DHCP OPNsense et l'assignation au bon bridge OVS selon le réseau cible (Dev, Prod ou DMZ).

    \item \textbf{Playbook 3 — Migration Dev vers Prod/DMZ :} gère la promotion d'une VM ou d'un ensemble de VMs vers la production ou la DMZ, en reconfigurant les interfaces réseau, les règles de pare-feu OPNsense et en vérifiant la connectivité post-migration.
\end{itemize}

\subsubsection{Pipeline PXE/TFTP}

\par Dans une optique de scalabilité, un pipeline de provisionnement automatique en deux phases a été mis en place pour intégrer tout nouveau serveur physique sans intervention manuelle.\\

\par \textbf{Phase 1 — Installation automatique via PXE.} Lorsqu'un nouveau serveur est mis sous tension, la séquence suivante s'exécute automatiquement :\\

\begin{enumerate}
    \item Le serveur envoie une requête DHCP ; OPNsense lui attribue une adresse temporaire et lui indique l'adresse du serveur de boot ainsi que le fichier bootloader à récupérer (options DHCP 66 et 67).
    \item Le firmware PXE contacte le serveur TFTP (UDP/69) pour télécharger le bootloader (\texttt{pxelinux.0}) et le kernel Linux d'amorçage. TFTP est le seul protocole utilisable dans un firmware pre-OS.
    \item Une fois le kernel démarré en mémoire, l'image d'installation Proxmox VE (\textasciitilde{}800 Mo) est téléchargée via HTTP depuis un serveur Nginx dédié. HTTP (TCP) est retenu pour ce transfert car TFTP (UDP) est inadapté aux fichiers volumineux.
    \item L'installateur Proxmox lit un fichier de réponses (\textit{Answer File}) hébergé sur le serveur HTTP, contenant le partitionnement, le nom d'hôte, le fuseau horaire et la langue. L'installation s'effectue sans aucune frappe clavier.
    \item Le serveur redémarre automatiquement sur Proxmox VE fraîchement installé.
\end{enumerate}

\par \textbf{Phase 2 — Intégration au cluster via Ansible.} À l'issue du redémarrage, le nœud dispose de Proxmox VE fonctionnel mais isolé. Un playbook Ansible prend le relais via SSH pour réaliser l'intégration complète :\\

\begin{itemize}
    \item Adhésion au cluster \textbf{Corosync} ;
    \item Configuration des interfaces \textbf{Open vSwitch} et des tunnels \textbf{VxLAN} ;
    \item Intégration des disques physiques comme \textbf{OSDs} dans le cluster \textbf{Ceph} ;
    \item Rattachement au groupe HA Proxmox (\texttt{sona-ha-group}) ;
    \item Déclaration du nœud comme cible dans \textbf{Prometheus}.
\end{itemize}

\par Ce découpage en deux phases répond à une contrainte fondamentale : PXE et TFTP interviennent dans un environnement pre-OS où aucun client SSH ne peut fonctionner, tandis qu'Ansible nécessite un système d'exploitation opérationnel. L'ensemble du pipeline permet l'ajout d'un nouveau nœud en moins de 25 minutes, sans intervention manuelle.\\

\subsection{\color{bleuu} Architecture du Cluster Ceph}

\subsubsection{Composants du Cluster}

\par Le cluster Ceph est composé des services suivants, répartis sur les trois nœuds physiques :\\

\begin{itemize}
    \item \textbf{Monitors (MON) :} un monitor par nœud, soit trois au total. Les monitors maintiennent la carte du cluster (\textit{cluster map}) et assurent le consensus distribué. Trois monitors garantissent un quorum stable (2/3 suffisants).
    \item \textbf{Managers (MGR) :} PVE-02 héberge le MGR actif, PVE-03 le MGR en standby. Le MGR expose les métriques du cluster via un endpoint REST utilisé par Prometheus.
    \item \textbf{OSDs (Object Storage Daemons) :} un OSD par nœud sur le disque \texttt{sdb} (300 GB SAS), soit trois OSDs contribuant au pool de stockage distribué.
\end{itemize}

\subsubsection{Dimensionnement du Pool}

\par Avec un facteur de réplication de 3, la capacité utilisable est calculée ainsi :\\

\[
\text{Capacité utilisable} = \frac{3 \times 300\ \text{GB}}{3} = 300\ \text{GB}
\]

\par L'algorithme CRUSH est configuré pour respecter les domaines de défaillance au niveau du nœud physique, garantissant que les trois répliques d'un même bloc ne se retrouvent jamais sur le même serveur. Le tableau suivant présente la répartition prévue :\\

\subsection{\color{bleuu} Contexte et Contraintes Réseau}

\par Le réseau Sonatrach met à disposition un sous-réseau \texttt{192.168.10.0/24} utilisé pour l'accès SSH et l'interface web Proxmox. La connectivité Internet des nœuds est assurée par un poste jouant le rôle de routeur externe à l'adresse \texttt{192.168.10.36}, qui réalise du NAT et du forwarding IP.\\

\par Le switch Sonatrach n'autorise que le VLAN 10 natif et ne permet pas la configuration de VLANs supplémentaires. Pour créer les réseaux logiques nécessaires à l'infrastructure, \textbf{VxLAN (Virtual Extensible LAN)} a été retenu comme technologie d'encapsulation. VxLAN permet de créer des réseaux logiques de niveau 2 tunnelisés au-dessus du réseau IP existant, sans modifier la configuration du switch. Open vSwitch gère la création et la terminaison de ces tunnels sur chaque nœud Proxmox.\\

\subsection{\color{bleuu} Topologie Réseau}

\subsubsection{Deux Niveaux de Segmentation}

\par La topologie retenue s'articule autour de deux niveaux complémentaires.\\

\par \textbf{Niveau 1 — Réseaux d'infrastructure (VxLAN inter-nœuds).} Pour les réseaux de contrôle (Corosync, Ceph Cluster, Ceph Public, Live Migration), des tunnels VxLAN point-à-point en maillage complet sont établis entre les trois nœuds. Chaque nœud crée deux ports VxLAN vers chacun des deux autres, garantissant une connectivité directe sans point de transit central.\\

\par \textbf{Niveau 2 — Réseaux applicatifs (OPNsense).} Pour les réseaux Dev, Prod et DMZ, une architecture centralisée autour d'une VM OPNsense est utilisée. Trois bridges OVS internes sont configurés sur chaque nœud. OPNsense dispose de quatre interfaces virtuelles : WAN connectée au réseau de management (\texttt{192.168.10.65}, gateway \texttt{192.168.10.36}), et trois interfaces LAN connectées aux bridges Dev, Prod et DMZ.\\

\subsection{\color{bleuu} Plan d'Adressage}

\par Le plan d'adressage est organisé en deux familles : les réseaux VxLAN d'infrastructure pour les flux de contrôle, et les réseaux applicatifs internes gérés par OPNsense.\\

\par \textbf{Réseaux VxLAN d'infrastructure :}
\begin{itemize}
    \item \textbf{VxLAN 10 — Management (192.168.10.0/24) :} Web UI Proxmox, SSH, API (réseau physique existant).
    \item \textbf{VxLAN 20 — Corosync (192.168.20.0/24) :} Heartbeats et quorum cluster.
    \item \textbf{VxLAN 30 — Ceph Cluster (10.10.30.0/24) :} Réplication OSD interne.
    \item \textbf{VxLAN 40 — Ceph Public (10.10.40.0/24) :} Accès des VMs au stockage RBD.

\begin{itemize}

    \item \textbf{Réseau Prod (172.16.70.0/24, gateway 172.16.70.1) :} environnements de production.
    \item \textbf{Réseau DMZ (172.16.80.0/24, gateway 172.16.80.1) :} services exposés, dont HAProxy.

\subsection{\color{bleuu} VM OPNsense : Routeur et Pare-feu Centralisé}

\subsubsection{Interfaces et Rôles}

\par La VM OPNsense constitue le cœur du réseau applicatif. Il s'agit d'une distribution FreeBSD dédiée aux fonctions de routage et de sécurité réseau. Dans cette architecture, OPNsense est déployée avec quatre interfaces réseau virtuelles :\\

\begin{itemize}
    \item \textbf{Interface WAN (192.168.10.65/24) :} connectée au bridge OVS de management, avec gateway \texttt{192.168.10.36}. Assure l'accès Internet sortant via NAT pour toutes les VMs internes.
    \item \textbf{Interface LAN1 (172.16.60.1/24) :} passerelle du réseau Dev.
    \item \textbf{Interface LAN2 (172.16.70.1/24) :} passerelle du réseau Prod.
    \item \textbf{Interface LAN3 (172.16.80.1/24) :} passerelle du réseau DMZ.
\end{itemize}

\par OPNsense intègre nativement dnsmasq, utilisé comme serveur DHCP pour les trois réseaux internes. L'attribution des adresses IP aux VMs est ainsi automatisée dès leur connexion à l'un des bridges applicatifs, simplifiant le provisionnement via les playbooks Ansible.\\

\subsubsection{Haute Disponibilité d'OPNsense}

\par OPNsense étant le point central du routage et du filtrage, sa défaillance isolerait l'ensemble des réseaux internes. Sa résilience est assurée par son intégration au groupe HA Proxmox. En cas de défaillance du nœud hébergeant la VM, Corosync la détecte et le HA Manager déclenche son redémarrage sur un nœud survivant, directement depuis le volume Ceph RBD. Le délai de basculement est de 60 à 120 secondes.\\

\par Pour une architecture de production nécessitant un basculement transparent, une configuration active/passive avec le protocole CARP (natif dans OPNsense) réduirait ce délai à moins de 5 secondes.\\

\subsection{\color{bleuu}Architecture du Pare-feu}

\subsubsection{Pare-feu OPNsense : Filtrage Inter-réseaux}

\par OPNsense applique les politiques de filtrage entre les réseaux applicatifs Dev, Prod et DMZ. Les règles de conception retenues sont les suivantes :\\

\par \textbf{Règles autorisées :}
\begin{itemize}
    \item Dev → WAN : autorisé pour les mises à jour et les dépôts de paquets.
    \item DMZ → WAN : autorisé pour les services exposés nécessitant un accès sortant.
    \item Prod → DMZ : autorisé pour la communication entre production et services exposés (HAProxy).
\end{itemize}

\par \textbf{Règles bloquées :}
\begin{itemize}
    \item Dev → Prod : bloqué pour isoler les environnements de développement de la production.
    \item Dev → DMZ : bloqué pour empêcher l'accès aux services exposés depuis le développement.
    \item Prod → WAN direct : bloqué, le trafic de production passe obligatoirement par la DMZ.
\end{itemize}

\subsubsection{Pare-feu Proxmox : Filtrage au Niveau Hyperviseur}

\par Proxmox VE intègre nativement un mécanisme de pare-feu basé sur iptables, configurable aux niveaux cluster, nœud et VM individuelle. Les règles de conception retenues pour protéger la plateforme sont les suivantes :\\

\begin{itemize}
    \item \textbf{Isolation des réseaux Ceph :} interdire tout trafic des réseaux applicatifs (\texttt{172.16.x.0/24}) vers les réseaux Ceph Cluster (VxLAN 30) et Ceph Public (VxLAN 40).
    \item \textbf{Isolation du réseau Corosync :} interdire tout accès extérieur au VxLAN 20. Seuls les nœuds Proxmox communiquent sur ce réseau.
    \item \textbf{Protection du management :} restreindre l'accès à l'interface web Proxmox (port \texttt{8006}) et SSH (port \texttt{22}) aux seules adresses du sous-réseau \texttt{192.168.10.0/24}.
    \item \textbf{Moindre privilège par VM :} n'autoriser que les ports applicatifs strictement nécessaires sur chaque VM.
\end{itemize}
