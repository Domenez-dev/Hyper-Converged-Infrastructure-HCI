\section{Introduction}

\par Ce chapitre présente la mise en œuvre concrète de la solution proposée dans le chapitre précédent. L'objectif est de montrer les étapes réelles de déploiement de l'infrastructure hyperconvergée, depuis l'installation de la plateforme de virtualisation jusqu'aux services applicatifs et aux mécanismes d'automatisation. Pour améliorer la lisibilité, l'implémentation est organisée en trois grandes parties : la couche calcul, la couche stockage, puis la couche réseau.\\

\par Les opérations ont été réalisées avec plusieurs outils complémentaires : l'interface web Proxmox VE, la ligne de commande Linux, les fichiers de configuration système, OPNsense, Ceph, ainsi que des playbooks Ansible pour automatiser certaines tâches répétitives. Des captures d'écran sont prévues aux points importants afin d'illustrer visuellement les résultats obtenus.\\

\section{Partie I: Couche Calcul}
% ============================================================

\par Cette partie couvre l'ensemble des opérations réalisées au niveau de la couche de calcul de l'infrastructure : installation de Proxmox VE, formation du cluster, déploiement du monitoring, implémentation du mécanisme CLBS, et déploiement des services applicatifs.

\subsection{Préparation de l'Infrastructure Physique}

\par La préparation de l'infrastructure physique constitue la première étape du déploiement. Elle comprend l'installation de Proxmox VE sur chaque nœud ainsi que la configuration de la connectivité réseau nécessaire au bon fonctionnement du cluster.

\subsubsection{Installation de Proxmox VE sur les nœuds}

\par L'installation de la plateforme de virtualisation a commencé par le téléchargement de l'image ISO de Proxmox VE version 9.1.1. Cette image a ensuite été copiée sur une clé USB bootable utilisée pour démarrer chaque serveur Dell PowerEdge R720. Une installation séparée a été réalisée sur chacun des trois nœuds du cluster.\\

\par Pendant l'installation, le disque système \texttt{sda} a été utilisé pour héberger Proxmox VE. Une configuration réseau statique a aussi été appliquée afin de donner à chaque nœud une adresse de management fixe sur le réseau physique \texttt{192.168.10.0/24}. Les adresses retenues sont \texttt{192.168.10.100} pour PVE-01, \texttt{192.168.10.213} pour PVE-02 et \texttt{192.168.10.84} pour PVE-03.\\

\par Une fois l'installation terminée, la vérification a été effectuée à travers l'interface web de Proxmox, accessible sur le port \texttt{8006}. Comme le montre la Figure~\ref{fig:proxmox-first-login}, cette étape a permis de confirmer que chaque nœud était opérationnel et prêt pour la suite du déploiement.\\

\subsubsection{Configuration de la connectivité Internet via le laptop gateway}

\par Dans l'environnement de laboratoire, aucun routeur physique dédié n'était disponible pour fournir l'accès Internet aux nœuds Proxmox. Pour cette raison, un laptop a été configuré pour jouer le rôle de passerelle NAT entre le réseau interne de l'infrastructure et Internet. Il possède deux interfaces : \texttt{enp0s20f0u4c2} côté infrastructure avec l'adresse \texttt{192.168.10.36/24}, et \texttt{wlan0} côté Internet avec l'adresse \texttt{10.247.78.8/24}.\\

\par La première étape consiste à activer le routage IP afin que le système puisse transférer les paquets d'une interface à l'autre. Cette activation doit être faite de manière immédiate puis rendue permanente.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Activation du routage IP sur le laptop},label={lst:ipforward}]
sudo sysctl -w net.ipv4.ip_forward=1
sudo vim /etc/sysctl.d/99-ipforward.conf
# Ajouter :
net.ipv4.ip_forward=1
\end{lstlisting}

\par Les commandes de la Figure~\ref{lst:ipforward} activent le forwarding IP : la première l'active immédiatement, la seconde le rend permanent via le fichier \texttt{99-ipforward.conf}. Sans cette étape, le laptop ne peut pas transmettre les paquets entre ses deux interfaces réseau.\\

\par Ensuite, des règles \texttt{iptables} ont été ajoutées pour réaliser la translation d'adresses NAT et autoriser le forwarding du trafic entre les interfaces du laptop.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Configuration NAT avec iptables},label={lst:iptables-nat}]
sudo iptables -t nat -A POSTROUTING -o wlan0 -j MASQUERADE
sudo iptables -A FORWARD -i enp0s20f0u4c2 -o wlan0 -j ACCEPT
sudo iptables -A FORWARD -i wlan0 -o enp0s20f0u4c2 -m state --state RELATED,ESTABLISHED -j ACCEPT
\end{lstlisting}

\par Les trois règles de la Figure~\ref{lst:iptables-nat} assurent respectivement : le masquage des adresses sources sur l'interface Internet, l'autorisation du trafic sortant, et l'autorisation des réponses correspondant à des connexions établies. Ensemble, elles permettent aux nœuds Proxmox d'atteindre Internet à travers le laptop.\\

\par Pour éviter de perdre ces règles après redémarrage, elles ont été sauvegardées puis activées automatiquement au boot du laptop.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Persistance des règles iptables},label={lst:iptables-persist}]
sudo pacman -S iptables-nft
sudo iptables-save | sudo tee /etc/iptables/iptables.rules
sudo systemctl enable iptables
\end{lstlisting}

\par Les commandes de la Figure~\ref{lst:iptables-persist} garantissent la persistance du NAT : la sauvegarde dans \texttt{/etc/iptables/iptables.rules} combinée à l'activation du service assure que le NAT sera opérationnel dès le démarrage du laptop, sans intervention manuelle à chaque redémarrage.\\

\par Sur chaque nœud Proxmox, la passerelle par défaut a été définie vers \texttt{192.168.10.36}, avec des serveurs DNS publics. \\Cette configuration a été ajoutée dans le fichier \texttt{/etc/network/interfaces}.\\

\begin{lstlisting}[style=sonacode,language={},caption={Configuration réseau de base d'un nœud Proxmox},label={lst:proxmox-basic-network}]
auto vmbr0
iface vmbr0 inet static
    address 192.168.10.XX/24
    gateway 192.168.10.36
    dns-nameservers 8.8.8.8 8.8.4.4
\end{lstlisting}

\par La configuration de la Figure~\ref{lst:proxmox-basic-network} attribue une adresse IP statique à chaque nœud, définit le laptop comme passerelle par défaut et utilise les DNS publics de Google. Le paramètre \texttt{XX} est remplacé par la valeur spécifique à chaque nœud (100, 213 ou 84).\\

\par Enfin, des routes statiques ont été ajoutées sur le laptop afin de rediriger les réseaux internes \texttt{172.16.60.0/24}, \texttt{172.16.70.0/24} et \texttt{172.16.80.0/24} vers la VM OPNsense, qui assure ensuite le routage vers ces sous-réseaux.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Ajout des routes statiques vers OPNsense},label={lst:static-routes-opnsense}]
nmcli connection modify "Wired connection 1" \
 +ipv4.routes "172.16.60.0/24 192.168.10.65" \
 +ipv4.routes "172.16.70.0/24 192.168.10.65" \
 +ipv4.routes "172.16.80.0/24 192.168.10.65"

nmcli connection up "Wired connection 1"
\end{lstlisting}

\par Les routes de la Figure~\ref{lst:static-routes-opnsense} indiquent au laptop que tout trafic destiné aux réseaux internes (\texttt{172.16.x.0/24}) doit être transmis vers l'adresse IP d'OPNsense (\texttt{192.168.10.65}), qui se charge du routage vers la zone applicative appropriée.\\

\par Des tests simples comme \texttt{ping 8.8.8.8}, \texttt{ping google.com} et \texttt{apt update} ont confirmé que les nœuds disposaient correctement d'un accès Internet.\\

\subsection{Formation du cluster Proxmox et haute disponibilité}

\par Après avoir installé et connecté les trois nœuds à Internet, l'étape suivante a consisté à les regrouper en un cluster unifié et à configurer les mécanismes de haute disponibilité.

\subsubsection{Création et jonction au cluster}

\par Après l'installation de Proxmox VE sur les trois serveurs, la phase suivante a consisté à former un cluster unique. Cette opération a été lancée depuis le premier nœud PVE-01, qui devient le nœud initial du cluster.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Création du cluster Proxmox},label={lst:pvecm-create}]
pvecm create Cluster-Proxmox-VE
\end{lstlisting}

\par La commande de la Figure~\ref{lst:pvecm-create} initialise le cluster sur PVE-01, configure automatiquement Corosync pour le mécanisme de heartbeat et génère les fichiers de configuration dans \texttt{/etc/pve/}. PVE-01 devient le nœud de référence pour les adhésions suivantes.\\

\par Les deux autres nœuds ont ensuite rejoint ce cluster en utilisant l'adresse IP du nœud principal.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Jonction de PVE-02 et PVE-03 au cluster},label={lst:pvecm-add}]
pvecm add 192.168.10.100
\end{lstlisting}

\par La commande de la Figure~\ref{lst:pvecm-add}, exécutée successivement sur PVE-02 et PVE-03, contacte le nœud initial, échange les certificats d'authentification et intègre le nœud au cluster Corosync existant.\\

\par Le réseau Corosync, utilisé pour le heartbeat entre les nœuds, a été isolé sur le VxLAN 20 afin de séparer le trafic de cluster du reste du trafic d'administration ou de production. Une fois la configuration terminée, la commande de vérification a confirmé la présence des trois nœuds avec quorum atteint.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Vérification de l'état du cluster},label={lst:pvecm-status}]
pvecm status
\end{lstlisting}

\par La commande \texttt{pvecm status} de la Figure~\ref{lst:pvecm-status} affiche l'état du cluster Corosync : nombre de membres actifs, version du quorum, et confirmation de l'atteinte du quorum. Une sortie avec \texttt{Quorum: Yes} et trois membres confirme que le cluster est correctement formé. Comme l'illustre la Figure~\ref{fig:cluster-three-nodes}, ce résultat est également visible dans l'interface web.\\

\subsubsection{Déploiement de Prometheus}

\par Prometheus a été installé dans le même conteneur afin de collecter les métriques exposées par Ceph et par le service applicatif CLBS. La configuration du fichier \texttt{prometheus.yml} contient deux jobs principaux : un job pour les métriques Ceph via le module MGR Prometheus, et un job pour l'application CLBS développée en Go.\\

\par Avant de configurer Prometheus, le module MGR Prometheus de Ceph a été activé sur les nœuds PVE-02 et PVE-03 via la commande suivante, exécutée une seule fois sur le cluster :

\begin{lstlisting}[style=sonacode,language=bash,caption={Activation du module Prometheus sur les nœuds Ceph},label={lst:ceph-prometheus-mon}]
ceph mgr module enable prometheus
\end{lstlisting}

\par Cette commande expose les métriques du cluster Ceph sur le port 9283 de chaque nœud hébergeant un MGR actif, permettant à Prometheus de les récupérer sans configuration supplémentaire côté Ceph.\\

\begin{lstlisting}[style=sonacode,language=yaml,caption={Extrait du fichier prometheus.yml},label={lst:prometheus-yml}]
global:
  scrape_interval: 30s
  evaluation_interval: 30s

scrape_configs:
  - job_name: ceph
    static_configs:
      - targets:
          - "192.168.10.213:9283"
          - "192.168.10.83:9283"
          - "192.168.10.100:9283"
        labels:
          cluster: "proxmox-lab"

  - job_name: "clbs"
    static_configs:
      - targets: ["192.168.10.104:9101"]
        scrape_interval: 30s
        scrape_timeout: 10s
\end{lstlisting}

\par la Figure~\ref{lst:prometheus-yml} définit deux jobs de collecte : le premier interroge les endpoints Ceph MGR des trois nœuds sur le port 9283, le second scrute le service CLBS sur le port 9101. L'intervalle de 30 secondes constitue un bon compromis entre fraîcheur des données et charge générée sur les cibles.\\

\par Après déploiement, l'interface web Prometheus a permis de confirmer que l'ensemble des cibles déclarées apparaissaient avec l'état \texttt{UP}, comme l'illustre la Figure~\ref{fig:prometheus-targets}.\\

\subsection{Implémentation du mécanisme CLBS}

\par Le mécanisme CLBS constitue l'une des contributions principales de ce projet. Il s'agit d'un service d'équilibrage proactif développé spécifiquement pour pallier l'absence de DRS natif dans Proxmox VE.

\subsubsection{Structure du service}

\par Le service CLBS (``Cluster Load Balancing Service'') a été développé en langage Go dans une VM dédiée accessible sur le réseau de management. Son rôle est d'analyser périodiquement la charge CPU du cluster et de déclencher automatiquement des migrations live lorsque cela est nécessaire.\\

\par Le code est structuré en plusieurs composants : un lecteur InfluxDB pour les métriques historiques, un client API Proxmox pour piloter le cluster, un calculateur de bandes de charge, et un moteur principal de décision. Les paramètres de connexion sont placés dans un fichier \texttt{.env} chargé au démarrage du service.\\

\subsubsection{Logique de décision}

\par À chaque cycle, le service récupère la charge des nœuds, calcule les bornes de charge modérée, puis classe les nœuds dans les catégories ``heavy'', ``moderate'' ou ``light''. Si un déséquilibre est détecté entre un nœud surchargé et un nœud léger, le moteur choisit la VM la plus adaptée à migrer.\\

\par Plusieurs mécanismes de protection ont été ajoutés pour éviter les migrations excessives, comme un temps de cooldown global, un cooldown individuel par VM et une suspension temporaire en cas de fréquence de migration trop élevée.\\

\subsubsection{Déploiement comme service systemd}

\par Une fois compilé, le binaire Go a été déployé sur la VM CLBS puis intégré comme service \texttt{systemd} afin d'assurer un démarrage automatique et une relance en cas de panne.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Gestion du service CLBS avec systemd},label={lst:clbs-systemd}]
systemctl enable clbs
systemctl start clbs
journalctl -u clbs.service -f -o cat
\end{lstlisting}

\par Les trois commandes de la Figure~\ref{lst:clbs-systemd} activent le démarrage automatique du service au boot, le démarrent immédiatement, et affichent les journaux en temps réel. Comme le montre la Figure~\ref{fig:clbs-logs}, ces journaux permettent de suivre en direct les décisions de migration et les éventuelles erreurs de connexion à l'API Proxmox ou à InfluxDB.\\

\begin{figure}[H]
    \centering

    \caption{Journaux systemd du service CLBS lors d'un cycle de détection et de migration.}
    \label{fig:clbs-logs}
\end{figure}

\par La Figure~\ref{fig:clbs-logs} présente la sortie de la commande \texttt{journalctl} pour le service CLBS pendant un cycle de détection actif. On y observe la classification des nœuds par bande de charge (heavy/moderate/light), la sélection de la VM candidate à la migration, le déclenchement de l'opération via l'API Proxmox et l'activation du cooldown post-migration.\\

\subsubsection{Validation du mécanisme}

\par Pour valider le comportement du service, deux VMs de test ont été créées puis soumises à une charge CPU artificielle avec l'outil \texttt{stress-ng}. Le service CLBS a détecté la surcharge et a déclenché une migration live vers un nœud moins chargé.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Génération d'une charge CPU de test},label={lst:stress-ng}]
stress-ng --cpu 8 --timeout 10m
\end{lstlisting}

\par La commande de la Figure~\ref{lst:stress-ng} lance 8 workers saturant les cœurs CPU disponibles. Cette surcharge artificielle déclenche la logique de détection du service CLBS qui, après vérification des seuils, sélectionne la VM candidate et initie sa migration vers un nœud moins chargé. Comme l'illustre la Figure~\ref{fig:clbs-migration-event}, le résultat est directement visible dans le dashboard dédié.\\

\begin{figure}[H]

\subsection{Automatisation avec Ansible}

\par L'automatisation est un élément clé de la reproductibilité de l'infrastructure. Les playbooks Ansible développés permettent de
provisionner de nouvelles VMs en quelques minutes et d'assurer leur intégration complète dans le cluster sans intervention
manuelle.

\subsubsection{Environnement et structure du projet}

\par Afin de simplifier le provisionnement des machines virtuelles et de rendre l'infrastructure plus reproductible, un
environnement Ansible a été mis en place. Les connexions se font via SSH depuis les postes des développeurs vers le réseau de
management, sans installation d'agent sur les nœuds cibles.\\

\begin{lstlisting}[style=sonacode,language={},caption={Structure du projet Ansible},label={lst:ansible-tree}]
ansible-infra/
├── ansible.cfg
├── secrets.yml
├── inventory/
│   ├── hosts.yml
│   └── proxmox_nodes.yml
└── playbooks/
    ├── bootstrap.yml
    ├── ntp_sync.yml
    ├── provision_vm.yml
    └── provision_vm_batch.yml
\end{lstlisting}

\par L'arborescence de la Figure~\ref{lst:ansible-tree} organise le projet en trois parties : les fichiers de configuration globaux à la racine, le répertoire
\texttt{inventory/} définissant les hôtes cibles, et le répertoire \texttt{playbooks/} contenant les scripts d'automatisation. Le
fichier \texttt{secrets.yml} est chiffré avec Ansible Vault pour protéger les identifiants sensibles.\\

\begin{lstlisting}[style=sonacode,language=ini,caption={Fichier ansible.cfg},label={lst:ansible-cfg}]
[defaults]
inventory            = inventory/hosts.yml
remote_user          = ansible
private_key_file     = ~/.ssh/ansible_ed25519
host_key_checking    = False
interpreter_python   = /usr/bin/python3

[privilege_escalation]
become      = True
become_user = root
\end{lstlisting}

\par Le fichier de configuration de la Figure~\ref{lst:ansible-cfg} définit l'utilisateur distant \texttt{ansible}, la clé SSH privée Ed25519 et l'élévation automatique de privilèges
vers \texttt{root}. La désactivation de \texttt{host\_key\_checking} simplifie le déploiement en environnement de laboratoire où
les hôtes changent fréquemment.\\

\subsubsection{Inventaire}

\par L'inventaire regroupe les nœuds Proxmox, les VMs permanentes administrées manuellement, ainsi qu'un groupe dynamique destiné
aux nouvelles VMs provisionnées à chaud par les playbooks.\\

\begin{lstlisting}[style=sonacode,language=yaml,caption={Extrait de l'inventaire hosts.yml},label={lst:ansible-hosts}]
all:
  children:
    proxmox_nodes:
      hosts:
        pve-01: {ansible_host: 192.168.10.100}
        pve-02: {ansible_host: 192.168.10.213}
        pve-03: {ansible_host: 192.168.10.84}
    managed_vms:
      hosts:
        ha-proxy:  {ansible_host: 192.168.10.111}
        app-1:     {ansible_host: 192.168.10.112}
        postgres:  {ansible_host: 192.168.10.115}
    provisioned_vms:
      hosts: {}
\end{lstlisting}

\par L'inventaire de la Figure~\ref{lst:ansible-hosts} est structuré en trois groupes : \texttt{proxmox\_nodes} pour les nœuds physiques, \texttt{managed\_vms} pour les
VMs permanentes, et \texttt{provisioned\_vms} initialement vide, alimenté dynamiquement via \texttt{add\_host} au moment de la
création de nouvelles machines.\\

\subsubsection{Playbook de provisionnement}

\par Le playbook \texttt{provision\_vm.yml} automatise la création d'une VM à partir d'un template Debian stocké dans le pool Ceph.
Il configure les ressources matérielles, le réseau via cloud-init, démarre la VM, puis la valide après boot.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Exemples d'utilisation du playbook
provision\_vm.yml},label={lst:ansible-vm-create}]
ansible-playbook playbooks/provision_vm.yml \
  -e "vm_id=110 vm_name=web-01"

ansible-playbook playbooks/provision_vm.yml \
  -e "vm_id=115 vm_name=db-01 vm_cores=4 vm_memory=8192"
\end{lstlisting}

\par Les deux exemples de la Figure~\ref{lst:ansible-vm-create} montrent la flexibilité du playbook : le premier crée une VM web avec les ressources par défaut, le second
provisionne une VM base de données avec 4 vCPUs et 8~Go de RAM. L'adresse IP est calculée automatiquement à partir du VMID.\\

\begin{lstlisting}[style=sonacode,language=yaml,caption={Formule d'attribution automatique de l'adresse
IP},label={lst:auto-ip-formula}]
vm_ip: "172.16.60.{{ vm_id | int - 90 }}"
\end{lstlisting}

\par La formule de la Figure~\ref{lst:auto-ip-formula} génère automatiquement une adresse IP cohérente à partir du VMID, évitant les conflits d'adressage. Par exemple,
la VM avec l'identifiant 110 reçoit l'adresse \texttt{172.16.60.20}.\\

\par La configuration cloud-init repose sur trois commandes successives : attachement du disque cloud-init, injection de la
configuration réseau, puis régénération de l'ISO cloud-init.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Configuration cloud-init d'une VM Proxmox},label={lst:cloud-init-qm}]
qm set {{ vm_id }} --ide2 {{ ceph_pool }}:cloudinit
qm set {{ vm_id }} --ipconfig0 ip={{ vm_cidr }},gw={{ vm_gw }} \
                   --nameserver {{ vm_dns }}
qm cloudinit update {{ vm_id }}
\end{lstlisting}

\par Les trois commandes de la Figure~\ref{lst:cloud-init-qm} attachent le disque cloud-init, injectent la configuration réseau (adresse IP, passerelle, DNS) et
régénèrent l'ISO afin que la VM applique ces paramètres dès son premier démarrage. Un second play se connecte ensuite directement à
la VM pour vérifier l'adresse IP configurée et effectuer une mise à jour complète des paquets.\\

\subsubsection{Playbook de bootstrap}

\par Une VM fraîchement créée ne possède pas encore l'utilisateur \texttt{ansible} ni sa clé SSH : elle ne peut donc pas être prise
en charge par les autres playbooks. Le playbook \texttt{bootstrap.yml} résout ce problème en prenant l'adresse IP de la cible en
paramètre, sans qu'elle figure préalablement dans l'inventaire.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Exemple d'utilisation du playbook
bootstrap.yml},label={lst:ansible-bootstrap}]
ansible-playbook playbooks/bootstrap.yml \
  -e "target_hosts=192.168.10.120" \
  -e "bootstrap_password=ROOT_PASS"
\end{lstlisting}

\par La commande de la Figure~\ref{lst:ansible-bootstrap} montre comment appeler ce playbook. Celui-ci se connecte en \texttt{root} avec le mot de passe fourni, installe \texttt{python3} et \texttt{sudo}, crée l'utilisateur
\texttt{ansible} avec les droits \texttt{sudo} sans mot de passe, puis déploie la clé publique SSH de gestion. À l'issue de ce
playbook, la VM est prête à être ajoutée à l'inventaire et prise en charge par les autres playbooks.\\

\subsubsection{Playbook de synchronisation NTP}

\par La cohérence temporelle entre les nœuds du cluster est indispensable pour Ceph et Corosync. Le playbook \texttt{ntp\_sync.yml}
configure \texttt{chrony} sur l'ensemble du parc en deux plays distincts.\\

\par Le premier play désigne \texttt{pve-01} comme maître NTP interne : il synchronise son horloge depuis \texttt{pool.ntp.org} et
la distribue aux sous-réseaux du cluster (\texttt{192.168.0.0/16} et \texttt{172.16.0.0/12}). Le second play configure tous les
autres nœuds en clients, avec \texttt{pve-01} comme source préférée et \texttt{pool.ntp.org} en secours. Chaque play se termine par
un appel à \texttt{chronyc tracking} pour vérifier l'état de synchronisation.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Exemples d'utilisation du playbook ntp\_sync.yml},label={lst:ansible-ntp}]
# Configurer tout le cluster
ansible-playbook playbooks/ntp_sync.yml

# Reconfigurer uniquement pve-02
ansible-playbook playbooks/ntp_sync.yml --limit "pve-02"

# Configurer des nœuds spécifiques uniquement
ansible-playbook playbooks/ntp_sync.yml --limit "app-1,postgres"
\end{lstlisting}

\par Les exemples de la Figure~\ref{lst:ansible-ntp} illustrent la flexibilité du playbook : la première invocation configure l'ensemble du cluster, la deuxième reconfigure uniquement PVE-02, et la troisième applique la configuration NTP à des nœuds spécifiques de l'inventaire sans impacter le reste du parc.\\

\subsubsection{Provisionnement en lot de VMs}

\par Le playbook \texttt{provision\_vm\_batch.yml} permet le provisionnement en lot de plusieurs VMs à partir d'une liste de
définitions YAML. Il itère sur cette liste via \texttt{include\_playbook} et invoque \texttt{provision\_vm.yml} pour chaque entrée,
en propageant les paramètres propres à chaque VM (identifiant, nom, ressources).\\

\begin{lstlisting}[style=sonacode,language=yaml,caption={Exemple de liste de VMs pour
provision\_vm\_batch.yml},label={lst:batch-vms}]
vms:
  - id: 110
    name: web-01
  - id: 111
    name: db-01
    cores: 4
    memory: 8192
\end{lstlisting}

\par L'exemple de la Figure~\ref{lst:batch-vms} illustre le provisionnement en lot de plusieurs machines virtuelles à partir d'une liste YAML. Cette automatisation porte sur le provisionnement des machines virtuelles au-dessus d'un cluster déjà opérationnel.
L'extension de cette même logique à l'amorçage des nœuds physiques eux-mêmes, c'est-à-dire l'installation initiale du système
d'exploitation via un pipeline PXE/TFTP, a fait l'objet d'une conception détaillée dans le chapitre précédent. Sa mise en œuvre
nécessitant toutefois du matériel serveur dédié, indisponible dans le cadre de ce projet, sa validation expérimentale est présentée
parmi les perspectives d'évolution de l'infrastructure.\\

\section{Partie II: Couche Stockage}
% ============================================================

\par La couche stockage repose entièrement sur Ceph, déployé directement en intégration native avec Proxmox VE. Cette section présente le déploiement du cluster Ceph et la validation de sa tolérance aux pannes.

\subsection{Déploiement du cluster Ceph}

\par Le déploiement du cluster Ceph suit une séquence bien définie : initialisation du réseau cluster, création des monitors et managers, ajout des OSDs, puis configuration du pool de stockage utilisé par les VMs.

\subsubsection{Initialisation de Ceph}

\par La couche stockage repose sur un cluster Ceph intégré directement à Proxmox. L'initialisation a été effectuée depuis l'interface web ou via la ligne de commande, en définissant un réseau cluster dédié et un réseau public séparé.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Initialisation du cluster Ceph},label={lst:ceph-init}]
pveceph init --network 10.10.30.0/24
\end{lstlisting}

\par La commande de la Figure~\ref{lst:ceph-init} initialise Ceph en spécifiant le réseau dédié aux échanges internes entre OSDs (\texttt{10.10.30.0/24}), transporté sur le VxLAN 30. Ce réseau est physiquement séparé du réseau public Ceph (\texttt{10.10.40.0/24}) pour isoler le trafic de réplication interne.\\

\par Le réseau \texttt{10.10.30.0/24} a été réservé aux échanges internes Ceph, tandis que le réseau \texttt{10.10.40.0/24} a été utilisé comme réseau public.\\

\subsubsection{Déploiement des MON et MGR}

\par Un moniteur Ceph a été créé sur chaque nœud du cluster afin d'assurer le quorum et la haute disponibilité des métadonnées du cluster.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Création d'un monitor Ceph},label={lst:ceph-mon-create}]
pveceph mon create
\end{lstlisting}

\par La commande de la Figure~\ref{lst:ceph-mon-create} est exécutée successivement sur chacun des trois nœuds. Avec trois monitors, le quorum Ceph est atteint dès que deux d'entre eux sont opérationnels, garantissant la disponibilité même en cas de panne d'un nœud.\\

\par Des managers Ceph ont aussi été déployés pour fournir les fonctions d'administration avancée et l'export des métriques vers Prometheus. Comme le montre la Figure~\ref{fig:ceph-mon-mgr}, l'interface Proxmox permet de vérifier l'état de l'ensemble des monitors et managers déployés.\\

\begin{figure}[H]
    \centering
    \includegraphics[width=1\textwidth]{image/ch4/ceph_mon_mgr.png}
    \caption{Interface Proxmox affichant les monitors et managers Ceph actifs sur les trois nœuds.}
    \label{fig:ceph-mon-mgr}
\end{figure}

\par La Figure~\ref{fig:ceph-mon-mgr} présente la vue Ceph de l'interface Proxmox après le déploiement des monitors et managers. Les trois MON apparaissent avec l'état \texttt{online} et le quorum est atteint, tandis que les MGR affichent leur rôle actif ou en veille selon le nœud, confirmant la redondance complète de la couche de contrôle Ceph.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Activation du module Prometheus pour Ceph},label={lst:ceph-prometheus}]
ceph mgr module enable prometheus
\end{lstlisting}

\par L'activation du module via la Figure~\ref{lst:ceph-prometheus} expose les métriques du cluster (état des OSDs, pools, latence, I/O) sur le port 9283 de chaque nœud, permettant à Prometheus de les collecter sans configuration supplémentaire côté Ceph.\\

\subsubsection{Déploiement des OSDs}

\par Sur chaque nœud, les quatre disques restants ont été intégrés comme OSDs Ceph. Le disque \texttt{/dev/sdb} (300~Go SAS) et les trois disques \texttt{/dev/sdc}, \texttt{/dev/sdd} et \texttt{/dev/sde} (600~Go SAS chacun) ont été provisionnés successivement via la commande suivante, exécutée pour chacun d'eux.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Création des OSDs Ceph sur chaque nœud},label={lst:ceph-osd-create}]
pveceph osd create /dev/sdb
pveceph osd create /dev/sdc
pveceph osd create /dev/sdd
pveceph osd create /dev/sde
\end{lstlisting}

\par Chaque appel à la Figure~\ref{lst:ceph-osd-create} formate le disque avec le système BlueStore et l'intègre comme OSD dans le cluster. La même séquence a été exécutée sur PVE-01, PVE-02 et PVE-03, portant le total à \textbf{douze OSDs} répartis équitablement sur les trois n\oe{}uds physiques.\\

\end{figure}

\par La Figure~\ref{fig:ceph-osd-health} affiche la vue OSD de l'interface Proxmox. Les douze OSDs apparaissent avec le statut \texttt{up/in}, leur type de stockage BlueStore et leur poids dans la hiérarchie CRUSH, confirmant que l'ensemble des disques est actif et correctement intégré au cluster.\\

\end{lstlisting}

Cette structure garantit que les trois répliques d'un même bloc seront toujours placées sur des serveurs physiques distincts, conformément à la politique de domaines de défaillance.\\

\subsubsection{Création du pool de stockage}

\par Un pool RBD a été créé avec une réplication de taille 3 et une taille minimale de 2, ce qui garantit la disponibilité des données même en cas de perte d'un nœud.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Création du pool Ceph},label={lst:ceph-pool-create}]
pveceph pool create ceph-pool --size 3 --min-size 2
\end{lstlisting}

\par Dans la Figure~\ref{lst:ceph-pool-create}, le paramètre \texttt{--size 3} impose trois répliques par objet, une par nœud physique. Le paramètre \texttt{--min-size 2} maintient le pool accessible tant qu'au moins deux répliques sont disponibles, offrant une tolérance à la panne d'un nœud sans coupure de service.\\

\par Ce pool a ensuite été intégré comme stockage partagé dans Proxmox pour héberger les disques des VMs et des conteneurs.\\

\end{lstlisting}

\par Les commandes de la Figure~\ref{lst:ceph-status} permettent de vérifier l'état du cluster : \texttt{ceph -s} affiche un résumé de l'état de santé, tandis que \texttt{ceph df} donne la capacité totale, utilisée et disponible par pool. Ces deux commandes constituent la vérification de base après chaque modification de la configuration Ceph. La Figure~\ref{fig:ceph-pool-health} illustre l'état du pool obtenu après ce déploiement.\\

\begin{figure}[H]

\end{figure}

\par La Figure~\ref{fig:ceph-pool-health} montre la vue des pools Ceph dans l'interface Proxmox. Le pool \texttt{ceph-pool} apparaît avec l'état \texttt{HEALTH\_OK}, le facteur de réplication à 3 et les métriques d'I/O en temps réel, confirmant le bon fonctionnement de la couche stockage.\\

\subsection{Validation de la tolérance aux pannes}

\par La tolérance aux pannes de la couche stockage a été vérifiée par un scénario de panne simulée. Lors de l'extinction d'un nœud, le cluster Ceph est passé temporairement à l'état \texttt{HEALTH\_WARN}, mais les données sont restées accessibles grâce au facteur de réplication.\\

\par Après le retour du nœud défaillant, Ceph a automatiquement lancé la resynchronisation des données et l'état du cluster est revenu à \texttt{HEALTH\_OK}. Ce test valide le bon comportement de la couche stockage distribuée.\\

\section{Partie III: Couche Réseau}
% ============================================================

\par La couche réseau est construite autour d'Open vSwitch et des tunnels VxLAN, permettant de créer plusieurs réseaux logiques isolés sur le même réseau physique Sonatrach. OPNsense assure le routage centralisé et le filtrage entre les différents segments.

\subsection{Configuration Open vSwitch et tunnels VxLAN}

\par La configuration réseau s'appuie sur Open vSwitch pour la création des bridges et des tunnels VxLAN, et sur les fichiers d'interfaces Linux pour la persistance de la configuration.

\subsubsection{Installation d'Open vSwitch}

\par Open vSwitch a été installé sur chaque nœud Proxmox afin de construire une couche réseau virtuelle flexible, adaptée au transport de plusieurs flux logiques sur le même réseau physique.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Installation d'Open vSwitch},label={lst:ovs-install}]
apt install openvswitch-switch
\end{lstlisting}

\par La commande de la Figure~\ref{lst:ovs-install} installe le daemon OVS et les outils de gestion en ligne de commande (\texttt{ovs-vsctl}, \texttt{ovs-ofctl}). Elle doit être exécutée sur chacun des trois nœuds Proxmox avant toute configuration des bridges et des tunnels.\\

\par Un bridge principal a été créé sur chaque nœud, puis l'interface physique principale y a été attachée pour servir de point de transit à tous les tunnels VxLAN.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Création du bridge OVS principal},label={lst:ovs-create-bridge}]
ovs-vsctl add-br vmbr0
ovs-vsctl add-port vmbr0 nic0
\end{lstlisting}

\par Les commandes de la Figure~\ref{lst:ovs-create-bridge} configurent le bridge principal : la première crée le bridge OVS \texttt{vmbr0}, la seconde y attache l'interface physique \texttt{nic0} comme port de transit. Tous les tunnels VxLAN créés ultérieurement utilisent ce bridge, permettant de transporter plusieurs réseaux logiques sur une seule interface physique.\\

\subsubsection{Configuration complète des interfaces (exemple sur PVE-01)}

\par Le fichier \texttt{/etc/network/interfaces} est presque le même sur les trois nœuds. La seule différence est l'adresse IP du bridge de management. La configuration présentée ici correspond à PVE-01 et sert d'exemple pour tout le cluster. \\

\par Chaque nœud doit connaître les adresses IP des autres car les tunnels VxLAN fonctionnent en mode point-à-point et ne disposent pas de découverte automatique. Avec une architecture VLAN, cette contrainte n'existerait pas, car Proxmox SDN permet de gérer et de distribuer automatiquement la configuration réseau depuis l'interface web. \\

\par Pour rendre la configuration plus facile à comprendre, elle est organisée en plusieurs parties selon le rôle des interfaces : réseau physique, réseaux Ceph et Corosync, migration et sauvegarde, puis réseaux applicatifs. La Figure~\ref{fig:pve01-overview} présente une vue d'ensemble avant le détail de chaque partie. \\

% Figure TikZ externalisée -- fichier : figures/fig_pve01_overview.tex
\input{image/ch4/fig_pve01_overview}

\par La Figure~\ref{fig:pve01-overview} illustre l'organisation en quatre couches de la configuration réseau de PVE-01 : le bridge de management (Partie 1), les VxLAN d'infrastructure Corosync et Ceph interne (Partie 2), les VxLAN de migration, Ceph public et sauvegarde (Partie 3), et enfin les VxLAN applicatifs avec leurs bridges Linux (Partie 4).\\

\paragraph{Partie 1: Interface physique et bridge de management}

\par Cette première partie définit l'interface physique \texttt{nic0} ainsi que le bridge OVS principal \texttt{vmbr0}, qui sert de point d'ancrage à l'ensemble des tunnels VxLAN. L'adresse de management \texttt{192.168.10.100/24} est attribuée directement sur ce bridge.\\

\begin{lstlisting}[style=sonacode,language={},caption={Interfaces de base et bridge OVS de management},label={lst:pve01-base}]
auto lo
iface lo inet loopback

iface nic0 inet manual

auto vmbr0
iface vmbr0 inet static
    address 192.168.10.100/24
    gateway 192.168.10.36
    ovs_type OVSBridge
    ovs_ports nic0

auto nic0
iface nic0 inet manual
    ovs_type OVSPort
    ovs_bridge vmbr0

iface nic1 inet manual
iface nic2 inet manual
iface nic3 inet manual

\subsection{Configuration du Pare-feu}

\par La sécurité réseau de l'infrastructure repose sur deux niveaux de
filtrage complémentaires et indépendants. Le premier est le pare-feu
OPNsense, qui assure le contrôle des flux entre les zones applicatives et
constitue la passerelle par défaut de toutes les machines virtuelles. Le
second est le pare-feu natif Proxmox, configuré au niveau de l'hyperviseur
pour protéger exclusivement les réseaux d'infrastructure internes (gestion,
cluster, stockage, migration). Cette séparation de responsabilités garantit
qu'un attaquant ayant compromis une VM applicative ne peut pas atteindre
directement les nœuds physiques du cluster.

% ------------------------------------------------------------
\subsubsection{Pare-feu OPNsense : Filtrage Inter-réseaux}
% ------------------------------------------------------------

\par OPNsense centralise le routage et applique les politiques de filtrage
entre les réseaux applicatifs Dev (\texttt{172.16.60.0/24}), Prod
(\texttt{172.16.70.0/24}) et DMZ (\texttt{172.16.80.0/24}). Toutes les
machines virtuelles utilisent OPNsense comme passerelle par défaut~: tout
flux entre zones ou vers Internet transite donc obligatoirement par ce
pare-feu. Les règles ont été configurées sous \texttt{Firewall\,>\,Rules}
selon le principe du moindre privilège~: tout flux non explicitement
autorisé est bloqué par la règle implicite \texttt{DENY ALL} placée en
dernière position.\\

% ------------------------------------------------------------
\subsubsection{Pare-feu Proxmox : Filtrage au Niveau Hyperviseur}
% ------------------------------------------------------------

\par En complément du filtrage OPNsense, le pare-feu natif Proxmox a été
configuré au niveau de l'hyperviseur pour protéger les réseaux
d'infrastructure. Ce pare-feu s'organise en trois niveaux hiérarchiques~:
le niveau \textit{datacenter} définit des objets réutilisables (alias,
IPSets, groupes de sécurité) sans appliquer de règles directement~; le
niveau \textit{nœud} référence ces groupes et fixe la politique par
défaut~; le niveau \textit{VM} ajoute uniquement les règles propres au rôle
de chaque machine. Chaque niveau hérite des objets définis au-dessus de lui,
ce qui évite toute redondance.\\

PostgreSQL (VM 205) & IN & ACCEPT & \texttt{App-1}, \texttt{App-2} & TCP 5432 — connexions SQL \\
\hline
\end{tabular}
\end{table}

\par HAProxy est la seule VM exposée vers l'extérieur sur le port
\texttt{8080}~; ses flux sortants sont restreints aux seuls backends Flask
identifiés par leurs alias. Le port \texttt{8404}, limité au réseau de
management, expose l'interface native de statistiques d'HAProxy. Les VMs
Flask n'acceptent le trafic applicatif que depuis l'alias \texttt{haproxy}
et n'émettent en sortie que vers PostgreSQL. La VM PostgreSQL n'accepte les
connexions SQL que depuis les deux backends Flask. La politique par défaut
\texttt{DROP} implicite bloque tout autre flux, assurant une isolation
stricte entre les composants de l'application.\\

\subsection{Système de Notification : Alertmanager}

\par La supervision active de l'infrastructure ne se limite pas à la visualisation des métriques : elle inclut la notification automatique des équipes en cas d'anomalie détectée. Le module Grafana Alerting a été configuré pour évaluer des règles d'alerte sur les métriques collectées et transmettre les notifications via un contact point Gmail utilisant le protocole SMTP.

\subsubsection{Configuration des règles d'alerte}

\par Les règles d'alerte sont définies directement dans Grafana sous ``Alerting -> Alert Rules''. Chaque règle spécifie une expression PromQL ou une requête InfluxDB, un seuil de déclenchement, une durée de maintien avant passage en état ``Firing'', et le groupe de contact destinataire.\\

\par Parmi les règles configurées figurent notamment celles décrites ci-dessous, chacune accompagnée de sa requête et de sa condition de déclenchement.\\

\par \textbf{Charge CPU élevée} sur les nœuds Proxmox -- requête Flux sur le bucket InfluxDB ``proxmox'', déclenchée lorsque l'utilisation moyenne dépasse 85~\% pendant 5 minutes (Figure~\ref{lst:alert-cpu}).\\

\begin{lstlisting}[style=sonacode,language={},caption={Règle d'alerte -- Charge CPU élevée sur les nœuds Proxmox},label={lst:alert-cpu}]
Source de donnees : InfluxDB (bucket "proxmox")

Requete (Flux) :
  from(bucket: "proxmox")
    |> range(start: -5m)
    |> filter(fn: (r) => r._measurement == "cpustat" and r._field == "cpu")
    |> last()

Condition : WHEN last() OF A IS ABOVE 85   (maintien 5 min -> Firing)
\end{lstlisting}

\par \textbf{RAM disponible faible} sur les nœuds Proxmox -- ratio mémoire utilisée / mémoire totale calculé via Flux, déclenché au-delà de 90~\% d'utilisation, soit moins de 10~\% de RAM disponible (Figure~\ref{lst:alert-ram}).\\

\begin{lstlisting}[style=sonacode,language={},caption={Règle d'alerte -- RAM disponible faible sur les nœuds Proxmox},label={lst:alert-ram}]
Source de donnees : InfluxDB (bucket "proxmox")

Requete (Flux) :
  from(bucket: "proxmox")
    |> range(start: -5m)
    |> filter(fn: (r) => r._measurement == "memory"
                     and (r._field == "memused" or r._field == "memtotal"))
    |> pivot(rowKey: ["_time"], columnKey: ["_field"], valueColumn: "_value")
    |> map(fn: (r) => ({ r with _value: float(v: r.memused) / float(v: r.memtotal) * 100.0 }))
    |> last()

Condition : WHEN last() OF A IS ABOVE 90   (RAM utilisee > 90 % <=> disponible < 10 %)
\end{lstlisting}

\par \textbf{OSD Ceph hors ligne} -- requête PromQL instantanée sur la métrique \texttt{ceph\_osd\_up}, déclenchée dès qu'un OSD passe à l'état arrêté (Figure~\ref{lst:alert-osd-down}).\\

\begin{lstlisting}[style=sonacode,language={},caption={Règle d'alerte -- OSD Ceph hors ligne},label={lst:alert-osd-down}]
Source de donnees : Prometheus (module mgr)

Requete (PromQL, instantanee) : ceph_osd_up

Condition : WHEN last() OF A IS BELOW 1
\end{lstlisting}

\par \textbf{Latence OSD anormale} -- requête PromQL instantanée sur \texttt{ceph\_osd\_apply\_latency\_ms}, déclenchée au-delà de 100~ms (Figure~\ref{lst:alert-osd-latency}).\\

\begin{lstlisting}[style=sonacode,language={},caption={Règle d'alerte -- Latence OSD Ceph élevée},label={lst:alert-osd-latency}]
Source de donnees : Prometheus (module mgr)

Requete (PromQL, instantanee) : ceph_osd_apply_latency_ms

Condition : WHEN last() OF A IS ABOVE 100
\end{lstlisting}

\par \textbf{Migrations excessives / circuit breaker CLBS} -- comptage des migrations sur 5 minutes via \texttt{increase(clbs\_migrations\_total[5m])}, déclenché au-delà de 5 migrations (Figure~\ref{lst:alert-clbs-migrations}).\\

\begin{lstlisting}[style=sonacode,language={},caption={Règle d'alerte -- Migrations excessives / circuit breaker CLBS},label={lst:alert-clbs-migrations}]
Source de donnees : Prometheus (exporter clbs:9101)

Requete (PromQL, instantanee) : increase(clbs_migrations_total[5m])

Condition : WHEN last() OF A IS ABOVE 5
\end{lstlisting}

\par \textbf{Erreurs API Proxmox / InfluxDB côté CLBS} -- comptage des erreurs de cycle sur 5 minutes via \texttt{increase(clbs\_cycle\_errors\_total[5m])}, déclenché dès qu'une erreur est détectée (Figure~\ref{lst:alert-clbs-errors}).\\

\begin{lstlisting}[style=sonacode,language={},caption={Règle d'alerte -- Erreurs API Proxmox / InfluxDB côté CLBS},label={lst:alert-clbs-errors}]
Source de donnees : Prometheus (exporter clbs:9101)

Requete (PromQL, instantanee) : increase(clbs_cycle_errors_total[5m])

Condition : WHEN last() OF A IS ABOVE 0
\end{lstlisting}

\par \textbf{Service CLBS indisponible} -- requête PromQL instantanée sur \texttt{up\{job="clbs"\}}, déclenchée lorsque la cible n'est plus joignable (Figure~\ref{lst:alert-clbs-down}).\\

\begin{lstlisting}[style=sonacode,language={},caption={Règle d'alerte -- Service CLBS indisponible},label={lst:alert-clbs-down}]
Source de donnees : Prometheus (exporter clbs:9101)

Requete (PromQL, instantanee) : up{job="clbs"}

Condition : WHEN last() OF A IS BELOW 1
\end{lstlisting}

\par Ces règles couvrent les scénarios de défaillance les plus critiques de l'infrastructure : surcharge des nœuds Proxmox, dégradation du cluster de stockage Ceph et indisponibilité du service d'équilibrage de charge CLBS.\\

\subsubsection{Déploiement de l'agent Grafana Alloy}

\subsection{Synchronisation Temporelle : NTP/Chrony}

\par La cohérence temporelle est une exigence fondamentale dans un cluster distribué. Une dérive de quelques secondes entre les nœuds peut perturber le quorum Corosync, fausser les journaux de corrélation et provoquer des incohérences dans les métriques Prometheus. Le serveur Chrony est hébergé directement sur \textbf{PVE-01} (\texttt{192.168.10.100}), qui fait référence pour l'ensemble des nœuds Proxmox et des VMs de l'infrastructure.

\subsubsection{Configuration du serveur Chrony sur PVE-01}

\par La configuration du fichier \texttt{/etc/chrony/chrony.conf} sur PVE-01 définit les serveurs de référence amont, la plage réseau des clients autorisés et le comportement de repli local.\\

\begin{lstlisting}[style=sonacode,language={},caption={Configuration du serveur Chrony sur PVE-01},label={lst:chrony-server-conf}]
# Serveurs NTP de reference amont
pool pool.ntp.org iburst

# Autoriser les clients du reseau de management
allow 192.168.10.0/24

# Fichier de derive
driftfile /var/lib/chrony/drift

# Repli local si perte de synchronisation amont
local stratum 10
\end{lstlisting}

\par Dans la Figure~\ref{lst:chrony-server-conf}, la directive \texttt{allow 192.168.10.0/24} couvre l'ensemble des nœuds Proxmox et des clients directs du réseau de management. Les VMs hébergées sur les VLANs \texttt{172.16.60/70/80.0/24} atteignent PVE-01 via un routeur qui effectue une translation d'adresses (NAT) : leurs requêtes NTP arrivent sur PVE-01 avec l'adresse source \texttt{192.168.10.65} (interface du routeur côté management), et sont donc couvertes par la même directive \texttt{allow} sans qu'il soit nécessaire d'y ajouter les sous-réseaux VLAN. La directive \texttt{local stratum 10} garantit que PVE-01 continue à distribuer une référence temporelle cohérente en cas de perte temporaire de connectivité vers \texttt{pool.ntp.org}.

\subsubsection{Configuration des clients NTP}

\par Sur chaque nœud Proxmox et sur chaque VM, le fichier \texttt{chrony.conf} client interroge PVE-01 en priorité, puis bascule vers \texttt{pool.ntp.org} si PVE-01 est indisponible.\\

\begin{lstlisting}[style=sonacode,language={},caption={Configuration Chrony côté clients (noeuds et VMs)},label={lst:chrony-client-conf}]
# Source primaire : serveur interne PVE-01
server 192.168.10.100 iburst prefer

# Fallback : serveurs publics si PVE-01 inaccessible
pool pool.ntp.org iburst

driftfile /var/lib/chrony/drift
\end{lstlisting}

\par La configuration de la Figure~\ref{lst:chrony-client-conf} interroge PVE-01 en priorité, avec bascule automatique vers \texttt{pool.ntp.org} si PVE-01 est indisponible. À la différence des conteneurs LXC qui héritent directement de l'horloge du nœud hôte, les VMs disposent d'une horloge virtuelle indépendante et nécessitent donc une synchronisation NTP explicite.

\subsubsection{Déploiement via Ansible}

\par La configuration NTP est appliquée sur les VMs via le playbook Ansible \texttt{ntp\_sync.yml}. Ce playbook est exécuté à la demande, en passant l'adresse IP de la VM cible, ce qui permet d'intégrer toute nouvelle machine dans la hiérarchie de synchronisation sans intervention manuelle. Le fonctionnement détaillé de l'automatisation Ansible est traité dans la section dédiée.

\par La vérification du bon fonctionnement du serveur Chrony s'effectue depuis PVE-01 via deux commandes complémentaires. La première confirme la connexion aux sources NTP amont, la seconde liste les clients actifs.\\

\subsection{Automatisation Opérationnelle : Rundeck}

\par La délégation de tâches opérationnelles récurrentes à une interface centralisée permet de réduire les erreurs humaines et de tracer l'ensemble des interventions sur l'infrastructure. Rundeck, déployé dans un conteneur LXC dédié, offre une interface web permettant de déclencher des playbooks Ansible sans accès SSH direct aux nœuds.

\subsubsection{Déploiement du LXC Rundeck}

\par Le conteneur LXC Rundeck a été créé sur le cluster Proxmox avec 2 vCPUs et 4 Go de RAM. Rundeck a été installé depuis les dépôts officiels et configuré pour écouter sur le port \texttt{4440}.\\

\begin{lstlisting}[style=sonacode,language=bash,caption={Installation de Rundeck},label={lst:rundeck-install}]
apt install -y rundeck
systemctl enable rundeckd
systemctl start rundeckd
\end{lstlisting}

\par Les commandes de la Figure~\ref{lst:rundeck-install} installent le service Rundeck, l'activent au démarrage et le démarrent immédiatement. Une fois actif, Rundeck est accessible via son interface web sur le port \texttt{4440} du conteneur LXC.\\

\subsubsection{Intégration du dépôt ansible-infra via GitLab Runner}

\par Après le déploiement du conteneur, le dépôt \texttt{ansible-infra} a été cloné depuis l'instance GitLab locale vers \texttt{/root} sur la machine Rundeck. Un ``GitLab Runner'' a ensuite été enregistré sur ce conteneur et intégré au pipeline CI/CD du dépôt.

\par Le rôle de ce runner est de synchroniser automatiquement les playbooks à chaque push validé : le pipeline copie le contenu du dépôt vers \texttt{/opt/ansible-infra}, répertoire appartenant à l'utilisateur système \texttt{rundeck} (\texttt{chown -R rundeck:rundeck /opt/ansible-infra}). Cette configuration garantit que Rundeck dispose des permissions nécessaires pour lire et exécuter les playbooks directement depuis ce répertoire, sans manipulation manuelle des fichiers.

\par Les clés SSH générées précédemment pour l'utilisateur \texttt{ansible} ont été déposées dans \texttt{/opt/ansible-infra/.ssh/}, rendant ce répertoire la source unique de vérité pour à la fois les playbooks et les secrets d'authentification SSH vers les VMs gérées.

\subsubsection{Définition des jobs}

\par Les jobs Rundeck ont été définis pour chaque opération récurrente de l'infrastructure. Chaque job référence le playbook Ansible correspondant dans \texttt{/opt/ansible-infra} et expose les variables nécessaires sous forme de paramètres saisissables dans l'interface web, permettant à un opérateur de déclencher une opération sans connaissance de la syntaxe Ansible.

\par Quatre jobs ont été configurés :

\begin{itemize}
  \item \textbf{Provision VM} : exécute \texttt{provision\_vm.yml}. Les paramètres exposés sont \texttt{vm\_id}, \texttt{vm\_name}, ainsi que des paramètres optionnels tels que \texttt{vm\_cores}, \texttt{vm\_memory} et \texttt{vm\_full\_clone} pour ajuster les ressources ou le mode de clonage.

  \item \textbf{Provision VM Batch} : exécute \texttt{provision\_vm\_batch.yml} pour le provisionnement en masse. Le paramètre principal est la liste des VMs à créer, passée sous forme de structure YAML.

  \item \textbf{Bootstrap VM} : exécute \texttt{bootstrap.yml} pour préparer une VM nouvellement créée à la gestion Ansible. Le paramètre exposé est \texttt{target\_hosts}, une liste d'adresses IP ou de noms d'hôtes (séparés par des virgules), permettant de cibler aussi bien des machines de l'inventaire que des IPs brutes.

  \item \textbf{NTP Sync} : exécute \texttt{ntp\_sync.yml} pour configurer ou resynchroniser chrony sur les nœuds. Le paramètre exposé est également \texttt{target\_hosts}, permettant de cibler un sous-ensemble de nœuds du cluster.
\end{itemize}
