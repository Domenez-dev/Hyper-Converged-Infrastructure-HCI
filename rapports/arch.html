Résumé des décisions d'architecture
Pourquoi Proxmox + Ceph + OVS
  • Stack légère, open source, sans licence
  • Proxmox gère calcul et hyperviseur (KVM)
  • Ceph assure le stockage distribué et répliqué
  • OVS segmente le réseau en VLANs logiciels
  • Tout-en-un sur petit cluster de 3 noeuds
Rôle de Open vSwitch (OVS)
  • Remplace un switch physique managé
  • Crée 3 VLANs isolés en logiciel
  • VLAN 20 protège le trafic Ceph des VMs
  • Gestion admin séparée du trafic utilisateur
  • Fonctionne entièrement en interne au host
Pourquoi 1 seul PC pour l'infra
  • WiFi entre PCs = Ceph instable (trafic continu)
  • Ethernet non disponible entre les deux PCs
  • Réseau interne au host = vitesse mémoire
  • 16GB RAM insuffisant pour split 2 PCs + Ceph
  • PC 2 devient station client uniquement
Architecture "Nested" Inception
  • Proxmox bare metal (Niveau 0) sur PC 1
  • 3 VMs Proxmox = noeuds cluster (Niveau 1)
  • Snapshot du cluster avant la démo possible
  • Migrable vers serveur Sonatrach sans refonte
  • Ceph MGR actif sur PVE-02, standby sur PVE-03
Scénario de démo (Sona-Web)
  • HAProxy equilibre entre Apache VM1 et VM2
  • PostgreSQL stocke son disque sur Ceph RBD
  • On éteint brutalement le noeud qui héberge PostgreSQL
  • Proxmox HA redémarre la VM sur un autre noeud
  • Aucune perte de donnée grace à Ceph (réplication x3)
Architecture cible (avec serveur Sonatrach)
  • 1 serveur physique 32GB+ RAM, 16 vCores
  • 3 grosses VMs = noeuds Proxmox (6-8GB chacune)
  • OSD disks de 100GB par noeud (300GB brut)
  • Pool Ceph : 150GB utilisables (replication x3)
  • Architecture documentée dans la these comme cible
